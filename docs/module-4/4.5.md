## The billion dollar mistake

Tony Hoare, who invented the null reference in 1965, later called it his *"billion dollar
mistake"*. `NullReferenceException` — using an object that is not there — has been the most
common crash in the industry ever since.

C# 8 added the countermeasure: **nullable reference types**. With `<Nullable>enable</Nullable>`
in the project file (on by default in new projects, and in this one), the *type itself* states
whether null is allowed:

```csharp
string name;       // must never be null - the compiler enforces it
string? name;      // may be null - the compiler makes you check before use
```

```csharp
string always = "here";
always.Length              // fine - cannot be null

string? maybe = GetInput();
maybe.Length               // WARNING: possible null dereference
maybe?.Length              // fine - null-safe
```

The crash becomes a compile-time warning, caught at your desk instead of in front of a user.

## The four null operators

You have met these piecemeal; here they are as a family:

| Operator | Reads as | Example |
|---|---|---|
| `?.` | "if not null, then…" | `person?.Address?.City` |
| `??` | "…otherwise use" | `name ?? "guest"` |
| `??=` | "assign only if null" | `user ??= "guest";` |
| `!` | "trust me, it is not null" | `maybe!.Length` |

```csharp
person?.Address?.City ?? "unknown"    // chains: null anywhere -> "unknown", no crash
maybeArray?[0]                        // works on indexers too
maybeArray?.Length ?? 0
```

`?.` short-circuits the whole rest of the chain the moment it meets a null — the same idea as
`&&` in [1.4](../module-1/1.4.md).

## Narrowing: the compiler follows your checks

This is the clever part. The compiler tracks *flow*: once you have checked, the warning
disappears because it **knows**:

```csharp
string? input = GetInput();

if (input is not null)
{
    input.Length          // no warning - provably not null here
}

if (string.IsNullOrEmpty(input))
    return;
input.ToUpper()           // no warning - IsNullOrEmpty told the compiler too
```

Patterns pull the same trick in one step:

```csharp
if (maybeName is { Length: > 2 } longName)    // non-null AND longer than 2, captured
    Console.WriteLine(longName);
```

## The `!` operator — handle with care

`!` (null-forgiving) switches the **check off**, not the danger:

```csharp
string? value = Definitely();
value!.Length             // warning silenced. If you were wrong: crash, as ever.
```

Legitimate uses are rare: you can *prove* the value is set but the compiler cannot see why
(a field assigned by a framework, a test arrangement). If you are typing `!` regularly, the
design is fighting you — restructure so the compiler can see the truth.

## Guard clauses at the boundary

The working pattern for a whole codebase: **check at the edges, be non-null inside**.

```csharp
static string Greet(string name)
{
    ArgumentNullException.ThrowIfNull(name);      // one-line guard
    return $"Hello, {name}";
}
```

Data from outside — user input, files, JSON, databases — gets validated once on arrival; the
interior of the program then deals only in honest, non-nullable types.

## `int?` and `string?` are different machinery

They look symmetric and are not:

| | `int?` | `string?` |
|---|---|---|
| Really is | `Nullable<int>` — a struct with a flag | the same `string` type |
| Exists at runtime | **yes** | no — annotation only |
| Enforcement | real: `.Value` on empty throws | warnings only |

```csharp
int? count = null;
count.HasValue            // false
count ?? -1               // -1
count.Value               // InvalidOperationException while null
```

The runtime consequence: because `string?` is compile-time fiction, **deserialised or external
data can still smuggle null in** past the annotations. That is exactly why the boundary-guard
pattern above exists.

## Practical rules

1. Leave `<Nullable>enable</Nullable>` on — always.
2. Default to non-nullable; add `?` only where null genuinely *means* something ("not found",
   "not set yet").
3. Validate at the boundary; stay non-null inside.
4. Return empty collections, never null collections.
5. Treat every `!` as a small debt — each one is a place the compiler can no longer help.

## Common mistakes

| Mistake | Result |
|---|---|
| Sprinkling `!` to silence warnings | The crashes return, now unwarned |
| `?.` on a chain, forgetting the result is nullable | The null pops out further down |
| Trusting annotations on external data | Runtime null sneaks past — validate |
| `string name = null!;` as a habit | Lying to the compiler at scale |

## Exercises

1. Write `Describe(Person?)` returning the city via `?.` chains with `??` fallbacks — no ifs.
2. Take a method full of `!` and refactor until none remain.
3. Show the difference: `int?` throwing on `.Value` versus `string?` merely warning.
4. Write a boundary guard for a `record Config(string Host, int Port)` deserialised from JSON,
   rejecting nulls the annotations claim cannot happen.
