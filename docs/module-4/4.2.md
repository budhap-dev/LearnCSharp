## Lambda syntax, from long to short

All four of these are the same function:

```csharp
Func<int, int> a = delegate (int x) { return x * x; };   // C# 2 anonymous method
Func<int, int> b = (int x) => { return x * x; };         // lambda, everything explicit
Func<int, int> c = (x) => x * x;                         // types inferred, expression body
Func<int, int> d = x => x * x;                           // one parameter needs no brackets
```

Read `=>` as **"goes to"**: *x goes to x squared*. The shapes:

```csharp
() => "no parameters"
x => x * 2                      // one parameter
(x, y) => x + y                 // two or more need brackets
n => { if (n < 0) return "neg"; return "pos"; }   // multi-statement needs braces + return
```

## Closures: a lambda remembers its surroundings

A lambda can use variables from the scope it was written in:

```csharp
int factor = 3;
Func<int, int> scale = n => n * factor;

scale(10)        // 30

factor = 10;
scale(10)        // 100  <- !
```

The lambda captured the **variable**, not its value at the time. Change `factor` later and the
lambda sees the change. This is called a *closure* — the function "closes over" its
environment.

### Captured state outlives the method

```csharp
static Func<int> MakeCounter()
{
    int count = 0;
    return () => ++count;       // count lives ON, owned by the lambda
}

var a = MakeCounter();
a(); a(); a();                  // 1, 2, 3
var b = MakeCounter();
b();                            // 1 - a completely separate count
```

`count` is a local variable of a method that has *finished* — yet it survives, privately, inside
each returned function. Each call to `MakeCounter` creates fresh state. This is genuinely
object-like behaviour with no class in sight.

## The loop-capture trap

```csharp
List<Func<int>> fs = new();
for (int i = 0; i < 3; i++)
{
    int copy = i;               // the safe habit
    fs.Add(() => copy);
}
fs.Select(f => f())             // 0, 1, 2
```

Capture `i` directly in an old-style `for` loop and every lambda shares **one** variable —
before C# 5 this printed `3, 3, 3`, and in `for` loops it still does. `foreach` was fixed to
give each iteration its own variable. The habit that is always safe: copy into a local before
capturing.

## Lambdas are what make LINQ readable

```csharp
words.Where(w => w.Length <= 4)
words.OrderBy(w => w.Length).ThenBy(w => w)
words.MaxBy(w => w.Length)
words.Sum(w => w.Length)
```

Each lambda is a tiny rule handed to the operator. Without lambdas, each would be a named
method three lines away — LINQ would technically work and practically be unreadable.

## static lambdas: refusing to capture

```csharp
Func<int, int> pure = static n => n * 2;
```

`static` on a lambda means "this captures **nothing**" — the compiler enforces it. Use it when
you want a guarantee that no accidental capture (and its hidden allocation) can creep in.

## Method groups: the lambda you do not need

When a lambda does nothing but forward to one method, pass the method name itself:

```csharp
strings.Select(s => int.Parse(s))    // works
strings.Select(int.Parse)            // same thing, cleaner
```

## Storing functions in data

Closures plus collections replace whole class hierarchies:

```csharp
Dictionary<string, Func<double, double, double>> operations = new()
{
    ["+"] = (x, y) => x + y,
    ["-"] = (x, y) => x - y,
    ["*"] = (x, y) => x * y,
    ["/"] = (x, y) => y == 0 ? double.NaN : x / y,
};

operations["*"](12, 4)      // 48
```

A command table like this drove the text adventure in project [7.3](../module-7/7.3.md).

## Common mistakes

| Mistake | Result |
|---|---|
| Capturing a `for` variable directly | Every lambda sees the final value |
| Assuming capture copies the value | It captures the variable — later changes show |
| Heavy work in a lambda inside a hot loop | Hidden cost — name it and measure |
| A 15-line lambda | Extract a named method; lambdas are for small rules |
