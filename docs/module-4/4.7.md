## The hierarchy

Exceptions are classes, and they inherit — which is what makes `catch` selective:

```
Exception
├── SystemException            thrown by the runtime
│     NullReferenceException, IndexOutOfRangeException, InvalidCastException...
├── ArgumentException          a caller passed something wrong
│     ├── ArgumentNullException
│     └── ArgumentOutOfRangeException
├── InvalidOperationException  right arguments, wrong TIME
├── IOException                files, streams, network
└── your own : Exception       problems specific to your domain
```

Catching `ArgumentException` also catches its two children — ordinary polymorphism
([2.6](../module-2/2.6.md)) applied to error handling.

## Catch order: most specific first

The first matching block wins, so specific handlers must come before general ones:

```csharp
try { result = 100 / int.Parse(input); }
catch (DivideByZeroException) { /* the zero case */ }
catch (FormatException)       { /* not a number */ }
catch (Exception ex)          { /* anything else - LAST */ }
```

Put `catch (Exception)` first and the compiler refuses: the later blocks would be unreachable.
One of C#'s politer guardrails.

## Exception filters: `when`

A filter decides *whether* to catch, without catching-and-rethrowing:

```csharp
catch (HttpLikeException ex) when (ex.StatusCode == 404)
{
    // handle "not found"
}
catch (HttpLikeException ex)
{
    // handle everything else
}
```

The subtle advantage: a filter that declines **never unwinds the stack**, so if the exception
goes unhandled, the debugger stops at the original throw with everything intact — better than
catch-test-rethrow in every way.

## `throw;` vs `throw ex;` — this one matters

```csharp
catch (InvalidOperationException ex)
{
    Log(ex);
    throw;          // re-throw: the ORIGINAL stack trace survives
}

catch (InvalidOperationException ex)
{
    Log(ex);
    throw ex;       // WRONG: the stack trace now starts HERE
}
```

`throw ex;` erases the trail back to where the problem actually happened — precisely the
information you will need at 2am. The lesson demonstrates both and counts the surviving stack
frames. The analyzer flags it (CA2200); believe it.

## Wrapping without losing the cause

Sometimes you *should* catch low-level exceptions and re-throw something meaningful — but
always carry the original along as `InnerException`:

```csharp
catch (IndexOutOfRangeException inner)
{
    throw new DataLoadException("Could not load the save file.", inner);
}
```

The caller gets a domain-level message; the debugger still has the full chain
(`ex.InnerException`). Losing the inner exception is losing the evidence.

## Custom exceptions

Inherit `Exception`, provide the three standard constructors, and carry **useful data**:

```csharp
public class InsufficientFundsException : Exception
{
    public InsufficientFundsException(decimal balance, decimal requested)
        : base($"Cannot withdraw {requested:F2}: the balance is only {balance:F2}.")
    {
        Balance = balance;
        Requested = requested;
    }

    public decimal Balance { get; }
    public decimal Requested { get; }
    public decimal Shortfall => Requested - Balance;
}
```

A catcher can now *act* on `ex.Shortfall` instead of parsing a message string. Write a custom
type when callers might handle your failure specifically; otherwise the built-ins
(`ArgumentException`, `InvalidOperationException`) already say it.

## The built-in guard helpers

One-liners for the checks every method needs:

```csharp
ArgumentNullException.ThrowIfNull(player);
ArgumentOutOfRangeException.ThrowIfNegative(lives);
ArgumentException.ThrowIfNullOrWhiteSpace(name);
```

## Throw, or return? The decision table

| Situation | Do |
|---|---|
| Caller broke the contract (null, out of range) | **throw** `Argument...Exception` |
| Right call, wrong state (withdraw from closed account) | **throw** `InvalidOperationException` |
| Failure is a normal outcome (bad user input, not found) | **return** `bool`/`TryX`/nullable |
| You caught it but cannot fix it | `throw;` — let it travel |
| Translating layers (parse error → "save file corrupt") | wrap, with `InnerException` |

The performance rule from [1.11](../module-1/1.11.md) still stands: exceptions are for
*exceptional* paths. The lesson times 20,000 catches against 20,000 `TryParse` calls —
hundreds of milliseconds versus about one.

## Common mistakes

| Mistake | Result |
|---|---|
| `throw ex;` | Stack trace destroyed |
| Wrapping without the inner exception | Evidence destroyed |
| `catch (Exception) { }` — swallow-all | Bugs resurface later, unexplained |
| Custom exception with no extra data | Noise — a built-in said it already |
| Exceptions as control flow | Slow and unreadable |
