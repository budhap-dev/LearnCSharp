## The problem

Some operations mostly *wait*: web requests, file reads, database queries. A thread that blocks
on them does nothing useful — in a UI the window freezes; on a server, a thread that could
serve other requests sits idle.

**Async lets a thread walk away from the wait and come back when the result is ready.**

## The shape of async code

```csharp
static async Task<int> FetchAsync(string name, int milliseconds)
{
    await Task.Delay(milliseconds);      // releases the thread while waiting
    return name.Length;
}
```

| Keyword | Meaning |
|---|---|
| `Task<int>` | a promise of an int, later |
| `Task` | a promise of completion, no value |
| `async` | this method may contain `await` |
| `await` | pause *here* without blocking; resume when done |

`await` unwraps the task: `int x = await FetchAsync(...)` reads like synchronous code and
frees the thread anyway. That readability is the entire point of the feature.

## Sequential await is still sequential

The lesson measures three 150 ms operations, three ways:

```csharp
// one at a time - awaited, but still ~450ms total
int x = await FetchAsync("A", 150);
int y = await FetchAsync("B", 150);
int z = await FetchAsync("C", 150);
```

The thread was free during each wait — good for the UI or server — but the *elapsed time* did
not improve. For that, overlap them:

```csharp
// start ALL THREE first, then wait once - ~150ms total
Task<int> a = FetchAsync("A", 150);      // running...
Task<int> b = FetchAsync("B", 150);      // running...
Task<int> c = FetchAsync("C", 150);      // running...

int[] results = await Task.WhenAll(a, b, c);
```

> **The rule:** calling an async method *starts* it. `await` only waits. Start everything that
> is independent, *then* await — `await f(); await g();` in sequence overlaps nothing.

`Task.WhenAny` resolves when the **first** finishes — the basis of races and timeouts.

## Exceptions in async code

`await` re-throws faithfully, so ordinary `try`/`catch` just works:

```csharp
try { await FailingAsync(); }
catch (InvalidOperationException ex) { ... }
```

With `WhenAll`, the *first* failure throws; the rest are on `task.Exception.InnerExceptions`
if you need the full list.

## Cancellation

Long operations should be interruptible. The pattern is cooperative — a token is passed down,
and the work checks it:

```csharp
using CancellationTokenSource cancellation = new();
cancellation.CancelAfter(TimeSpan.FromSeconds(2));

try
{
    await LongJobAsync(cancellation.Token);
}
catch (OperationCanceledException) { /* stopped in time */ }
```

Pass the token to every async call that accepts one (`Task.Delay`, HTTP, file I/O all do) so
the *wait itself* can be interrupted.

## The rules that keep you out of trouble

| Never | Because | Instead |
|---|---|---|
| `.Result` / `.Wait()` | blocks; can **deadlock** UI apps | `await` |
| `async void` | exceptions escape and kill the process | `async Task` (exception: event handlers) |
| `Thread.Sleep` in async code | blocks the thread you freed | `await Task.Delay` |
| Fire-and-forget without care | failures vanish silently | await it, or store the task |

"Async all the way down": once a call chain contains an `await`, the callers become async too.
Resist the temptation to bottle it up with `.Result` — that is where deadlocks live.

## Async is for waiting, not for working

Async helps when the CPU is *idle* — I/O, network, timers. It does nothing for computation:
awaiting a calculation still computes on somebody's thread.

For CPU-bound work, move it explicitly:

```csharp
int[] counts = await Task.WhenAll(
    Task.Run(() => CountPrimes(1, 25_000)),
    Task.Run(() => CountPrimes(25_000, 50_000)));
```

`Task.Run` puts work on a pool thread; two halves genuinely run in parallel on two cores. The
lesson measures the speedup. The threading story continues in [6.1](../module-6/6.1.md).

| Work type | Tool |
|---|---|
| I/O-bound (waiting) | `async`/`await` |
| CPU-bound (computing) | `Task.Run`, `Parallel.For` |

## Common mistakes

| Mistake | Result |
|---|---|
| `await` in a row for independent work | No overlap — start first, then await |
| `.Result` on a task | Deadlock risk, blocked thread |
| `async void` methods | Uncatchable exceptions |
| Forgetting to pass the CancellationToken down | The job cannot actually be cancelled |
| `Task.Run` around I/O | A thread now waits — pointless |

## Exercises

1. Simulate three downloads (100/200/300 ms). Run sequentially, then with `WhenAll`; print
   both elapsed times.
2. Race a slow operation against `Task.Delay(500)` with `WhenAny` to implement a timeout.
3. Add cancellation to a counting loop; cancel after one second and observe where it stops.
4. Split a prime count across four `Task.Run` calls and compare with one.
