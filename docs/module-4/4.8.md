## Stack and heap, properly this time

[2.8](../module-2/2.8.md) introduced the split; here is the full picture:

| Thing | Lives on | Freed |
|---|---|---|
| Value-type local | the **stack** | instantly, when the method returns |
| Object (`new` anything) | the **heap** | later, by the garbage collector |
| Reference variable | arrow on stack → object on heap | arrow with the method; object by GC |
| Field of an object | the heap, inside its owner | with its owner |

The stack is automatic and free. The heap needs management — and in C#, the **garbage
collector** (GC) is that management.

```diagram

```

## How the GC thinks: generations

The GC's core insight: **most objects die young**. So the heap is split by age:

```
gen 0   brand new objects        collected often, very cheap
gen 1   survived one collection  collected sometimes
gen 2   long-lived survivors     collected rarely, expensive
```

An object nobody references any more is garbage; a collection finds the live objects and
reclaims the rest. You saw it happen in the lesson — 100,000 abandoned arrays, then a
collection, and the memory returns.

> **Never call `GC.Collect()` in real code.** The lesson does it once, to demonstrate. The
> runtime schedules collections better than you can.

## What the GC does *not* do

The GC frees **managed memory**. It knows nothing about the things your objects hold on to
outside the runtime:

- file handles
- network sockets
- database connections
- graphics resources

An abandoned `FileStream` will eventually be collected — but the *operating system file handle*
stays open until then, which may be minutes later, and meanwhile the file is locked. These need
deterministic cleanup: **`IDisposable`**.

## IDisposable and using

```csharp
public sealed class FakeFile : IDisposable
{
    public void Dispose()
    {
        if (IsDisposed) return;          // must be safe to call twice
        IsDisposed = true;
        // release the handle here
    }
}
```

You *could* call `Dispose` manually — but any exception between open and close skips it. The
`using` statement guarantees it:

```csharp
using (FakeFile file = new("safe.txt"))
{
    file.Write("hello");
}                                        // Dispose runs HERE - even if Write threw
```

`using` compiles to `try { ... } finally { Dispose(); }` — the `finally` from
[1.11](../module-1/1.11.md) doing its one great job.

The brace-free **using declaration** disposes at the end of the enclosing scope:

```csharp
using FakeFile file = new("safe.txt");
file.Write("hello");
// disposed when the method ends
```

Stacked usings dispose in **reverse order** — inner first, like nested scaffolding.

## The disposables you will actually meet

| Type | Wraps |
|---|---|
| `StreamReader` / `StreamWriter` | file handles ([4.9](4.9.md)) |
| `FileStream` | raw file access |
| `HttpClient` | sockets — but create **one** and share it, app-wide |
| `SqlConnection` | database connections |
| `CancellationTokenSource` | ([4.10](4.10.md)) |

Rule of thumb: if a type implements `IDisposable`, you `using` it — unless its documentation
says otherwise (`HttpClient` is the famous exception).

## Managed memory leaks — yes, they exist

The GC only frees what nothing references. "Leak" in C# means *accidentally keeping a
reference*:

| Leak | Mechanism |
|---|---|
| Event subscriptions | publisher holds every subscriber alive ([4.3](4.3.md)) — unsubscribe |
| Static collections | anything added to a static list lives forever |
| Closures | a lambda keeps its captured objects alive ([4.2](4.2.md)) |
| Undisposed resources | the handle outlives its usefulness |

## Boxing: value types visiting the heap

Assigning a value type into an `object` **copies it onto the heap** — a hidden allocation
called *boxing*:

```csharp
object boxed = 42;         // box: heap allocation, copy in
int unboxed = (int)boxed;  // unbox: copy back out
```

One box is nothing. A million in a loop is GC pressure. This is the final piece of the
[3.4](../module-3/3.4.md) story: generics exist largely so that `List<int>` stores real ints —
the old `ArrayList` boxed every single element.

## Common mistakes

| Mistake | Result |
|---|---|
| Not disposing a stream | File stays locked until some later GC |
| `GC.Collect()` sprinkled around | Slower, not faster |
| Events never unsubscribed | Long-lived leak |
| A second `Dispose` throwing | Guard it — dispose must be idempotent |
| Boxing in a hot loop | Invisible allocations, GC churn |

## Exercises

1. Write a `TempFolder : IDisposable` that creates a temp directory and deletes it on dispose.
   Prove with `using` that it cleans up even when the body throws.
2. Demonstrate the event leak: a static publisher, a subscriber that is never collected, then
   fix with `-=`.
3. Sum 10 million ints via `List<int>` and via `List<object>`; time both and explain the gap.
4. Find every `IDisposable` in your project 7.4 code and check each is properly `using`-ed.
