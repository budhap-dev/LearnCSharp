## The idea

An **event** lets an object announce "*this just happened*" to whoever cares, without knowing
who is listening — or whether anyone is.

```csharp
public class TickTimer
{
    public event Action<int>? Tick;             // the announcement channel

    public void RunFor(int seconds)
    {
        for (int second = 1; second <= seconds; second++)
            Tick?.Invoke(second);               // announce - the ?. matters
    }
}
```

```csharp
timer.Tick += OnTick;                           // a named method subscribes
timer.Tick += s => Console.WriteLine($"lambda saw tick {s}");

timer.RunFor(3);                                // both listeners fire, three times
timer.Tick -= OnTick;                           // unsubscribe
```

The publisher and its subscribers are completely **decoupled**: the timer knows nothing about
logging or UI or sound; each subscriber knows nothing about the others. This is the Observer
pattern ([2.14](../module-2/2.14.md)) built into the language.

## Why `event`, not a plain delegate field?

A `public Action<int>? Tick` field would *almost* work — but any outside code could:

```csharp
timer.Tick = null;               // wipe everyone else's subscriptions
timer.Tick.Invoke(999);          // fire the event from outside
```

The `event` keyword restricts outsiders to `+=` and `-=` **only**. Assigning and invoking are
reserved for the declaring class. Same multicast machinery as [4.1](4.1.md), with the access
rules an announcement channel needs.

## The `?.Invoke` idiom

An event with no subscribers is `null`. This is why every raise looks like:

```csharp
Tick?.Invoke(second);            // fires only if someone is listening
```

Writing `Tick.Invoke(...)` crashes the publisher the moment nobody happens to be subscribed —
one of the most common event bugs.

## Carrying data: the standard .NET pattern

Real .NET events follow one convention, and following it makes your events feel native:

```csharp
public class BasketEventArgs : EventArgs
{
    public BasketEventArgs(string item, decimal total) { Item = item; Total = total; }
    public string Item { get; }
    public decimal Total { get; }
}

public class Basket
{
    public event EventHandler<BasketEventArgs>? ItemAdded;

    public void Add(string item, decimal price)
    {
        Total += price;
        OnItemAdded(new BasketEventArgs(item, Total));
    }

    // protected virtual OnX method, so subclasses can extend the raise
    protected virtual void OnItemAdded(BasketEventArgs e) => ItemAdded?.Invoke(this, e);
}
```

```csharp
basket.ItemAdded += (sender, e) => Console.WriteLine($"added {e.Item}, total {e.Total:F2}");
```

| Convention | Detail |
|---|---|
| Delegate type | `EventHandler<TEventArgs>` |
| Signature | `(object? sender, TEventArgs e)` |
| Data class | inherits `EventArgs`, immutable |
| Naming | past tense: `Clicked`, `Saved`, `ItemAdded` |
| Raising | via a `protected virtual OnX` method |

`sender` tells a subscriber *which* object raised it — useful when one handler watches many.

## The unsubscription trap

`-=` removes a handler by **reference equality**. You can only remove what you kept:

```csharp
timer.Tick += s => Console.WriteLine(s);        // anonymous - GONE forever
timer.Tick -= s => Console.WriteLine(s);        // a DIFFERENT lambda - removes nothing
```

Store the delegate if you will ever need to detach it:

```csharp
Action<int> handler = s => Console.WriteLine(s);
timer.Tick += handler;
timer.Tick -= handler;                           // works
```

This matters beyond tidiness: **a publisher holds a live reference to every subscriber**. A
long-lived publisher keeps short-lived subscribers alive — the classic managed-memory leak
([4.8](4.8.md)). Long-running apps must unsubscribe.

## Where events fit

| Scenario | Events? |
|---|---|
| UI: button clicked, key pressed | ✅ the canonical use |
| Model notifying observers (score changed, health hit zero) | ✅ — project [7.3](../module-7/7.3.md) does this |
| One object calling one known collaborator | ❌ just call the method |
| Wanting a return value back from listeners | ❌ events are fire-and-forget |

## Common mistakes

| Mistake | Result |
|---|---|
| `Tick.Invoke(...)` without `?.` | Crash when nobody subscribed |
| `-=` with a fresh lambda | Silently removes nothing |
| Never unsubscribing in a long-lived app | Memory leak |
| Public delegate field instead of `event` | Outsiders can wipe or fire it |
| Expecting results back from handlers | Use a `Func` parameter instead |
