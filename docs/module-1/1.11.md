## The three kinds of error

| Kind | When | Told about it? |
|---|---|---|
| **Syntax** | Compile time — the code breaks C#'s rules | Yes, with a file and line. The easy ones. |
| **Runtime** (exception) | While running — divide by zero, missing file | Yes, it crashes |
| **Logic** | Never | **No.** It runs happily and gives the wrong answer |

```csharp
int x = 5                          // SYNTAX: missing semicolon
int y = numbers[99];               // RUNTIME: IndexOutOfRangeException
double average = total / count;    // LOGIC: integer division, silently wrong
```

Logic errors are the expensive ones. Only **testing** finds them.

## try / catch

```csharp
try
{
    int result = int.Parse(userInput);
}
catch (FormatException)
{
    Console.WriteLine("That was not a number.");
}
```

Catch the **specific** exception you expect. Order matters: most specific first, because the
first matching block wins.

```csharp
try { ... }
catch (DivideByZeroException) { ... }    // specific
catch (FormatException)       { ... }    // specific
catch (Exception ex)          { ... }    // catch-all goes LAST
```

Putting `catch (Exception)` first is a compile error — the later blocks would be unreachable.

## finally

Runs on **every** path out of the `try` — normal end, `return`, or exception:

```csharp
try      { reader = new StreamReader("data.txt"); Process(reader); }
catch    (FileNotFoundException) { Console.WriteLine("No such file."); }
finally  { reader?.Dispose(); }      // ALWAYS runs
```

In practice you use `using` instead, which does the same thing more neatly —
[4.8](../module-4/4.8.md).

## The exceptions you will actually meet

| Exception | Cause |
|---|---|
| `NullReferenceException` | Used an object that is not there |
| `IndexOutOfRangeException` | Array index outside `0 … Length-1` |
| `ArgumentOutOfRangeException` | Same idea, for `List` and method arguments |
| `DivideByZeroException` | Integer division by zero |
| `FormatException` | `int.Parse("abc")` |
| `OverflowException` | The number is a number, but too big |
| `InvalidCastException` | A cast that is not valid at run time |
| `KeyNotFoundException` | `dictionary["missing"]` |
| `InvalidOperationException` | Right arguments, wrong time (e.g. modifying during `foreach`) |
| `FileNotFoundException` | The file is not there |

## NullReferenceException

Its inventor, Tony Hoare, called null his *"billion dollar mistake"*. Modern C# helps: declare
`string?` to mean "this might be null" and the compiler warns when you forget to check.

```csharp
string? name = FindUser(id);
Console.WriteLine(name.Length);    // compiler WARNING
Console.WriteLine(name?.Length);   // safe: gives null instead of crashing
if (name is not null) { ... }      // checked - warning gone
```

Full treatment in [4.5](../module-4/4.5.md).

## Reading a stack trace

```
System.InvalidOperationException: Something broke deep down.
   at LevelThree()      <- where it actually broke
   at LevelTwo()        <- who called that
   at LevelOne()        <- who called that
   at Run()
```

**Read from the top.** The first line is where it broke; each line below is the caller. Find the
first line that mentions **your** file — that is almost always where your bug is.

## Throwing your own

```csharp
static void SetAge(int age)
{
    if (age < 0)
        throw new ArgumentOutOfRangeException(nameof(age), "Age cannot be negative.");
    ...
}
```

`nameof(age)` turns the parameter name into the string `"age"`. Rename the parameter later and
the message follows automatically — a rename can never leave a stale string behind.

## Exceptions are slow

Do **not** use them for ordinary validation. Run the lesson to see the real numbers — throwing
20,000 exceptions takes hundreds of milliseconds; 20,000 `TryParse` calls take about one.

```csharp
try { n = int.Parse(s); } catch (FormatException) { n = 0; }   // slow, noisy
if (!int.TryParse(s, out int n)) n = 0;                        // fast, clear
```

## Debugging, cheapest technique first

1. **Read the error message.** It names the exception, the message, the file and the line.
   Students who skip this waste hours.
2. **Print the values.** `Console.WriteLine($"i={i} total={total}")` inside the loop. Crude,
   instant, and it solves most bugs.
3. **Use a breakpoint.** In VS Code or Visual Studio, click the margin next to a line and press
   **F5**. The program pauses there and you can hover over variables.
   - **F10** step over · **F11** step into · **Shift+F11** step out · **F5** continue
4. **Rubber-duck it.** Explain the code out loud, line by line. You will usually spot the bug
   mid-sentence.
5. **Bisect.** Comment out half the code. Still broken? The bug is in the other half. Repeat.
   This is binary search applied to your own program.
6. **Assert your assumptions.** `Debug.Assert(count >= 0)` fires only in Debug builds.

## Golden rules

- **Never write an empty `catch { }`.** Swallowing an error just moves the symptom somewhere
  else, later, with no clue where it came from.
- **If you cannot handle it, do not catch it.** Let it travel up to code that can.
- **Do not catch `Exception`** at the point of failure — catch the specific type.
- **Validate, do not catch,** for expected bad input.

## Exercises

1. Write a method that parses an int from a string, returning a default on failure — once with
   `try`/`catch`, once with `TryParse`. Time both over 100,000 bad inputs.
2. Deliberately cause each of the ten exceptions in the table above and practise reading the
   traces.
3. Take a program you wrote earlier and make it survive *any* input a user could type.
4. Set a breakpoint inside a loop, run it, and step through five iterations watching the
   variables change.
