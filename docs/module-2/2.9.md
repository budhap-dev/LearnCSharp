# 2.9 — Records and immutable data

> **Run it:** `dotnet run --project src/LearnCSharp.Lessons -- 2.9`
> **Code:** [`L09_Records.cs`](../../src/LearnCSharp.Lessons/Lessons/M2_Oop/L09_Records.cs)

## One line, a whole type

```csharp
public record PersonRecord(string FirstName, string LastName, int Age);
```

That single line generates: init-only properties, a constructor, `ToString`, `Equals`,
`GetHashCode`, `==`/`!=`, a `Deconstruct` method, and a `with` copier.

The class equivalent is about 40 lines, and you have to keep every part of it in step by hand.

## Records compare by value

This is the headline difference:

```csharp
var ada  = new PersonRecord("Ada", "Lovelace", 36);
var same = new PersonRecord("Ada", "Lovelace", 36);

ada == same                    // true  - same values
ReferenceEquals(ada, same)     // false - different objects

// with a plain class:
classA == classB               // false - different objects, full stop
```

A record asks *"do these hold the same data?"*. A class asks *"are these literally the same
object?"*.

## `with` makes a modified copy

```csharp
PersonRecord older = ada with { Age = 37 };
// ada is untouched
```

Rather than mutating, you produce a new value with one thing changed. This is the core habit of
immutable programming, and it removes a whole class of "who changed this behind my back?" bugs.

## Deconstruction

```csharp
(string first, string last, int age) = ada;
(string title, string author, _) = book;      // _ discards
```

Free on positional records. See [4.6](../module-4/4.6.md).

## Records can have bodies

They are not limited to one line — validation, computed properties and methods all work:

```csharp
public record Temperature
{
    public Temperature(double celsius)
    {
        if (celsius < -273.15)
            throw new ArgumentOutOfRangeException(nameof(celsius), "Below absolute zero.");

        Celsius = celsius;
    }

    public double Celsius { get; init; }

    public double Fahrenheit => Celsius * 9 / 5 + 32;

    public string Description => Celsius switch
    {
        < 0 => "freezing", < 15 => "cold", < 25 => "mild", _ => "warm",
    };
}
```

## Records support inheritance

```csharp
public record Employee(string FirstName, string LastName, int Age, string Department)
    : PersonRecord(FirstName, LastName, Age);
```

Note that the generated `Equals` also checks the exact record type, so a `PersonRecord` never
equals an `Employee` even with identical names.

## `record struct`

```csharp
public readonly record struct Coordinate(int X, int Y);
```

Value semantics **and** generated members. Ideal for small data you copy a lot — coordinates,
money, RGB colours. Because equality and hashing come free, they work perfectly as dictionary
keys and in hash sets:

```csharp
HashSet<Coordinate> visited = [new(0, 0), new(1, 1), new(0, 0)];
visited.Count                        // 2 - the duplicate collapsed
visited.Contains(new Coordinate(1, 1))  // true
```

## The trap: records containing collections

```csharp
public record Player(string Name, List<string> Inventory);

var a = new Player("Ada", ["sword"]);
var b = new Player("Ada", ["sword"]);

a == b     // FALSE
```

The generated `Equals` compares each member — and `List<string>` compares by **reference**. Two
lists holding the same strings are still two different lists.

Fixes: compare contents explicitly with `SequenceEqual`, or use an immutable collection type.
This is not a bug in records; it is `List<T>`'s equality showing through.

## When to use what

| Use a… | When | Example |
|---|---|---|
| `record` | data defined by its values | DTOs, settings, coordinates, events |
| `class` | it has identity and changing state | `BankAccount`, `Player`, `Game` |
| `struct` | a small value copied often | `Point`, `Money`, `Colour` |

A `BankAccount` should **not** be a record: two accounts with the same balance are not the same
account. A `Coordinate` should be: (3, 4) *is* (3, 4).
