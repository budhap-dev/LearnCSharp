## The two measures that matter

**Coupling** — how much classes depend on each other. You want it **low**.

```csharp
// TIGHT - welded to SQL Server           // LOOSE - any storage will do
class OrderService                        class OrderService
{                                         {
    SqlDatabase _db = new();                  readonly IRepository _repo;
}                                         }
```

**Cohesion** — how focused one class is. You want it **high**.

```csharp
// LOW - unrelated jobs in one class      // HIGH - each does one thing
class Everything                          class Invoice     { CalculateVat(); Total(); }
{                                         class EmailSender { Send(); }
    CalculateVat();                       class FileStore   { Save(); }
    SendEmail();
    SaveToDisk();
    ParseCsv();
}
```

Every principle below is a specific technique for getting **high cohesion, low coupling**.

## S — Single Responsibility

> A class should have one reason to change.

```csharp
// BAD - three reasons to change: report format, file format, mail server
class Report { Generate(); SaveToFile(); Email(); }

// GOOD
class Report    { Generate(); }
class FileSaver { Save(report); }
class Mailer    { Send(report); }
```

The test is not "does it do one thing?" but **"who would ask for this to change?"** If the
finance team and the IT team would both request changes to the same class, it has two
responsibilities.

## O — Open/Closed

> Open to extension, closed to modification.

```csharp
// BAD - a switch you must edit every time a shape is invented
double Area(Shape s) => s.Type switch { "circle" => ..., "square" => ... };

// GOOD - each shape knows its own area
abstract class AreaShape { public abstract double Area(); }
```

Adding a `Pentagon` now means writing **one new class**. No existing file is touched, so no
existing behaviour can break. This is polymorphism ([2.6](2.6.md)) doing real work.

## L — Liskov Substitution

> A subclass must work anywhere its parent works, without surprises.

The classic violation is making `Square` inherit `Rectangle`:

```csharp
rect.Width = 5;
rect.Height = 4;
// caller expects Area() == 20
// but if rect is really a Square, setting Width also sets Height -> 16
```

The subclass **broke a promise the parent made**. The fix: they are siblings, not parent and
child — both implement `IAreaShape`.

> Symptoms of a violation: a subclass that throws `NotSupportedException`, silently ignores a
> setter, or forces the caller to check its type first.

## I — Interface Segregation

> Many small interfaces beat one large one.

```csharp
// BAD - an old printer must implement Scan() and Fax() it cannot do
interface IMachine { Print(); Scan(); Fax(); }

// GOOD
interface IPrinter { Print(); }
interface IScanner { Scan(); }
class AllInOne : IPrinter, IScanner { }
```

No class should be forced to implement members it has no use for.

## D — Dependency Inversion

> Depend on abstractions, not on concrete classes.

```csharp
// BAD - welded to email
class AlertService { EmailMessageSender _s = new(); }

// GOOD - anything that can send
class AlertService
{
    private readonly IMessageSender _sender;
    public AlertService(IMessageSender sender) => _sender = sender;
}
```

```csharp
new AlertService(new EmailMessageSender());   // production
new AlertService(new RecordingSender());      // test - captures, sends nothing
```

**This is what makes code testable.** No mail server, no network, no waiting. It is the single
most valuable principle of the five for everyday work.

## Three more worth knowing

| | Means |
|---|---|
| **DRY** — Don't Repeat Yourself | the same *knowledge* should live in exactly one place |
| **YAGNI** — You Aren't Gonna Need It | do not build for a future that may never arrive |
| **Law of Demeter** | talk to your friends, not your friends' friends |

```csharp
order.Customer.Address.Postcode.Trim()   // BAD - knows four levels of structure
order.CustomerPostcode()                 // GOOD
```

> DRY is about knowledge, not characters. Two identical lines that would change for *different
> reasons* are not duplication — merging them creates coupling.

## Apply them sensibly

> ⚠️ SOLID is a set of **heuristics, not laws**. Splitting a 20-line program into nine classes
> and four interfaces is worse, not better.

Apply a principle when you feel the pain it removes:

| Pain | Principle |
|---|---|
| One change forces edits in five files | Single responsibility |
| Every new type means editing a `switch` | Open/closed |
| A subclass keeps surprising callers | Liskov |
| Implementing an interface means writing stubs that throw | Interface segregation |
| You cannot test it without a database | Dependency inversion |

## Exercises

1. Find a class you have written that has two responsibilities. Split it.
2. Rewrite a `switch` over a type as polymorphism, and add a new case to both versions. Which
   was easier?
3. Write a `Notifier` that takes an `IMessageSender`, plus a fake sender, and test it without
   sending anything.
4. Find a Law of Demeter violation in your code and fix it with one method.
5. Give an example where applying SOLID would be over-engineering.
