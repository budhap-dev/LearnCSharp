## The idea

**Abstraction** means deciding what to show and what to ignore.

You rely on it constantly without noticing:

| You write | You do not need to know |
|---|---|
| `Console.WriteLine("hi")` | how text reaches the screen |
| `list.Sort()` | which sorting algorithm it used |
| turning a steering wheel | the entire steering mechanism |
| flicking a light switch | the National Grid |

## A driver's view of a car

```csharp
public class FamilyCar
{
    private double _fuel = 50;
    private bool _running;
    private int _gear;

    public string FuelGauge => $"{_fuel:F1} litres";

    public string Start()
    {
        PrimeFuelPump();
        EngageStarterMotor();
        Ignite();
        _running = true;
        return "engine started";
    }

    // --- none of this is any of the driver's business ---
    private void PrimeFuelPump() { }
    private void EngageStarterMotor() { }
    private void Ignite() { }
}
```

Three public members. Behind them the class ran the fuel pump, the starter motor and the
ignition — and the driver never had to know.

```
what the driver sees          what actually happens
--------------------          ---------------------
car.Start()             ->    PrimeFuelPump()
                              EngageStarterMotor()
                              Ignite()
car.Drive(30)           ->    SelectGear(30)
                              BurnFuel(30)
```

## Abstraction vs encapsulation

These get confused constantly. The distinction is worth learning properly:

| | Abstraction | Encapsulation |
|---|---|---|
| Is a… | **design** idea | **mechanism** |
| Concerns | the **outside** — what users of your class see | the **inside** — protecting the data |
| Question it answers | "what should I expose?" | "how do I stop that being broken?" |
| In code | choosing to have `Start()` at all | `private` fields and validating setters |

> **In one line:** abstraction *chooses* the simple view; encapsulation *enforces* it.

## Levels of abstraction

```
your game code          player.Attack(goblin)
game engine             sprite.Animate("swing")
graphics library        DrawTriangle(v1, v2, v3)
driver                  write to GPU register 0x40
hardware                voltages
```

Each layer offers a simpler view of the one below. This is how something as complicated as a
modern computer stays comprehensible to a human.

## `abstract` classes: a partly-finished blueprint

```csharp
public abstract class PaymentMethod
{
    public abstract string Name { get; }

    // abstract = no body. Every concrete child MUST supply one.
    public abstract string Pay(decimal amount);

    // Written once here, inherited by all of them.
    public string Receipt(decimal amount) => $"Receipt: {amount:C} paid by {Name}";
}

public class CardPayment : PaymentMethod
{
    public override string Name => "card";
    public override string Pay(decimal amount) => $"charged {amount:C} to card";
}
```

`PaymentMethod` defines **what** every payment does without saying **how**. You cannot write
`new PaymentMethod()` — there is nothing to run. That is the point.

## Interfaces: abstraction with no implementation at all

| | `abstract class` | `interface` |
|---|---|---|
| Contains | some *what*, some *how* | pure *what* |
| How many per class | one | as many as you like |
| Can hold fields | yes | no |

More in [2.7](2.7.md).

## Choosing the right level

```csharp
// Too little - the caller must know everything
engine.PrimeFuelPump();
engine.EngageStarter();
engine.Ignite();

// Too much - it does not say enough to be useful
car.DoThing("start");

// Right - one clear intention
car.Start();
```

**Every public member should express an intention, not a step.**

## Leaky abstractions

An abstraction *leaks* when the details it hid start to matter anyway.

`list.Sort()` hides the algorithm — until your list is ten million items and suddenly you must
care. `File.ReadAllText` hides the disk — until the file is on a slow network share.

No abstraction is perfect. The goal is to be right *almost* all the time, and to fail
understandably when it is not.

## Designing an abstraction

Four questions:

1. Who uses this, and what are they actually trying to achieve?
2. What is the smallest set of members that lets them do it?
3. What might I want to change later without breaking them?
4. Does every public member express an **intention**, not a step?
