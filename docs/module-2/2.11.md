## `static`: belonging to the class, not the object

```csharp
public class Counter
{
    private static int _created;        // ONE field, shared by every Counter

    public Counter()
    {
        _created++;
        Id = _created;
    }

    public int Id { get; }                     // per object
    public static int Created => _created;     // per class
}
```

Three `Counter` objects each get their own `Id`, but they all share one `_created`.

A static member is reached through the **class**: `Counter.Created`, never `myCounter.Created`.

## Static classes

```csharp
public static class MathHelper
{
    public static bool IsEven(int n) => n % 2 == 0;
    public static int Gcd(int a, int b)
    {
        while (b != 0) (a, b) = (b, a % b);
        return a;
    }
}
```

No state, no instances — just functions. `new MathHelper()` will not compile. `Math`, `Console`
and `File` are all static classes.

## Static constructors

```csharp
static Settings()
{
    Version = "1.0.3";
}
```

Runs automatically, exactly once, before anything in the class is first touched. No access
modifier, no parameters, and you never call it yourself.

## Composition: HAS-A instead of IS-A

```csharp
public class Car
{
    private readonly Engine _engine;        // a Car HAS AN Engine

    public Car(string model, Engine engine)
    {
        Model = model;
        _engine = engine;
    }

    public string Start() => _engine.Start();
}
```

A `Car` is not a kind of `Engine`, so inheritance would be wrong. It is *built from* one.

```csharp
new Car("Mini", new Engine(1300));           // petrol
new Car("Leaf", new ElectricEngine(150));    // electric - same Car class
```

The part can be swapped **at run time**, which inheritance can never do.

## Composition vs inheritance

| | Inheritance | Composition |
|---|---|---|
| Decided | compile time | **run time** |
| How many | one base class | as many parts as you like |
| Coupling | tight — you inherit everything | loose — only what you use |
| Testing | must construct the whole hierarchy | swap a part for a fake |

> The standard advice is **"favour composition over inheritance"**. Use inheritance when the
> child genuinely IS A kind of the parent *and* you want its behaviour. Otherwise compose.

## Dependency injection

Composition made explicit: rather than building its own collaborators, a class is **handed**
them.

```csharp
public class Game
{
    private readonly ILogger _logger;

    public Game(ILogger logger) => _logger = logger;    // injected, not created

    public string Play()
    {
        _logger.Log("Game started");
        return "finished";
    }
}
```

```csharp
new Game(new ConsoleLogger());   // real
new Game(new MemoryLogger());    // test - captures messages, prints nothing
```

Had `Game` written `new ConsoleLogger()` internally, you could never test it without printing,
and never reuse it in a web app. One constructor parameter buys all of that flexibility.

Lesson 6.5 takes this further with a real DI container.

## The SOLID principles

Covered properly in [2.13](2.13.md), but in one line each:

| | Principle | Means |
|---|---|---|
| **S** | Single responsibility | one class, one reason to change |
| **O** | Open/closed | open to extend, closed to modify |
| **L** | Liskov substitution | a child must work anywhere its parent does |
| **I** | Interface segregation | many small interfaces beat one huge one |
| **D** | Dependency inversion | depend on `ILogger`, not `ConsoleLogger` |

## When static is the wrong tool

Static is convenient and therefore over-used. It is **global state**, and global state:

- cannot be swapped for a test double
- hides dependencies (nothing in the signature says the method touches it)
- causes race conditions once threads are involved ([6.1](../module-6/6.1.md))

Static is fine for **pure functions** — same input, same output, no state — like `Math.Sqrt`.
Be suspicious of static *data*.

## Common mistakes

| Mistake | Result |
|---|---|
| `myObject.StaticMember` | Compile error — use the class name |
| Static mutable state | Untestable, and unsafe once threaded |
| Inheriting purely to reuse code | Tight coupling and a fragile hierarchy |
| `new`ing dependencies inside a class | Impossible to test in isolation |
| A "Utils" static class that grows forever | Low cohesion — split it up |
