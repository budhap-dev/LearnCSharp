## The idea

An interface is a **contract**: a list of things a class promises to provide, with no
implementation attached.

```csharp
public interface IStorage
{
    void Save(string key, string value);
    string? Load(string key);
}
```

No bodies, no fields, no constructor. Just the promise. Naming convention: interfaces start
with a capital `I`.

## Implementing it

```csharp
public class MemoryStorage : IStorage
{
    private readonly Dictionary<string, string> _data = new();

    public void Save(string key, string value) => _data[key] = value;
    public string? Load(string key) => _data.GetValueOrDefault(key);
}

public class CloudStorage : IStorage { /* completely different innards */ }
```

`MemoryStorage` and `CloudStorage` share **no** code and no base class. They are related only by
the promise they both keep.

## Why this is powerful

```csharp
static string SaveGame(IStorage storage, string player)
{
    storage.Save("current", player);
    return "saved";
}
```

`SaveGame` does not know or care which storage it was handed. Swap a file for a database for a
test double — `SaveGame` never changes.

> **Program to the interface, not the implementation.** This one habit is what makes code
> testable, and it is the D in SOLID ([2.13](2.13.md)).

## A class may implement many

```csharp
public class Robot : IMovable, ISpeaker
{
    public string Move()  => $"{Name} rolls forward.";
    public string Speak() => $"{Name} beeps.";
}
```

This is how C# gets the flexibility of multiple inheritance without the ambiguity. A class has
**one** base class but **any number** of interfaces.

## Interfaces you already use

| Interface | Gives you |
|---|---|
| `IEnumerable<T>` | works with `foreach` and all of LINQ ([3.5](../module-3/3.5.md)) |
| `IComparable<T>` | `Sort()` knows how to order your type |
| `IDisposable` | works with `using` ([4.8](../module-4/4.8.md)) |
| `IEquatable<T>` | efficient equality |

Implementing `IComparable<T>` is how you teach the framework to sort your own type:

```csharp
public class Student : IComparable<Student>
{
    // negative = I come first, 0 = equal, positive = I come later
    public int CompareTo(Student? other) => other is null ? 1 : other.Mark.CompareTo(Mark);
}

students.Sort();      // now works
```

## Default implementations (C# 8+)

An interface may supply a default body:

```csharp
public interface ISpeaker
{
    string Speak();

    string Introduce() => $"I am a {GetType().Name} and I can speak.";
}
```

Implementers get `Introduce` free. One catch worth knowing: it lives on the **interface**, so
you reach it through an interface reference:

```csharp
((ISpeaker)robot).Introduce();     // ✅
robot.Introduce();                 // ❌ does not compile
```

Use this sparingly — mainly to add a member to a published interface without breaking everyone
who already implements it.

## Explicit implementation

When two interfaces demand the same member name, or you want a member reachable *only* through
the interface:

```csharp
public class Duck : IFlyer
{
    public string Fly() => "Duck flaps its wings.";       // the class's own
    string IFlyer.Fly() => "IFlyer.Fly on a Duck.";       // explicit
}
```

## Interface vs abstract class

| | Interface | Abstract class |
|---|---|---|
| Is a | contract | partly-built base |
| Fields / state | ❌ | ✅ |
| Constructor | ❌ | ✅ |
| How many per class | many | **one** |
| Shared code | only defaults | yes |

**Rule of thumb:** use an interface for a *capability* (`ICanBeSaved`, `IMovable`); use an
abstract class when several classes genuinely share a base **and** some implementation.

When unsure, start with an interface. It is the looser choice, and loose is easier to change.

## Common mistakes

| Mistake | Fix |
|---|---|
| `public` on interface members | They are public by definition — it will not compile |
| Trying to add a field to an interface | Use a property, or an abstract class |
| One giant interface | Split it — the I in SOLID ([2.13](2.13.md)) |
| Depending on the concrete class | Take the interface as a parameter |
