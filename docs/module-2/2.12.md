## The five relationships

| Relationship | Reads as | Example |
|---|---|---|
| **Inheritance** | IS-A | a Dog is an Animal |
| **Composition** | HAS-A, and owns it | a House has Rooms — they die with it |
| **Aggregation** | HAS-A, but shares it | a Team has Players — they outlive it |
| **Dependency** | USES-A | a Printer uses a Document, briefly |
| **Association** | KNOWS-A | a Student knows their Teacher |

They are listed roughly strongest to weakest. **Prefer the weakest one that does the job** —
weaker means easier to change.

## Composition — the part cannot exist without the whole

```csharp
public class House
{
    private readonly List<Room> _rooms = new();

    // The House CREATES the Room
    public void AddRoom(string name, double area) => _rooms.Add(new Room(name, area));
}
```

Demolish the house and the rooms are gone. In UML: a **filled** diamond on the House end.

## Aggregation — the part exists independently

```csharp
public class Team
{
    private readonly List<TeamPlayer> _players = new();

    // The Team is GIVEN a player it did not create
    public void Sign(TeamPlayer player) => _players.Add(player);
}
```

Disband the team and the players carry on; one player can join another team. In UML: a
**hollow** diamond.

> **The test:** *did this object create the part, or was it handed one?* Created → composition.
> Handed → aggregation.

## Dependency — a passing acquaintance

```csharp
public class Printer
{
    // Receives a Document, uses it, forgets it. No field, no ownership.
    public string Print(Document document) => $"printing \"{document.Title}\"";
}
```

The weakest coupling there is, and usually the best. If a parameter will do, do not make it a
field.

## Association — they know each other

```csharp
public class SchoolStudent
{
    public Teacher? Tutor { get; private set; }

    public void AssignTutor(Teacher teacher)
    {
        Tutor = teacher;
        teacher.AddTutee(this);        // keep both ends in step
    }
}
```

Bidirectional associations are easy to get wrong: if you set one end you must set the other, or
the model becomes inconsistent. Prefer one-directional where you can.

## The arrows

```
Dog ------|>  Animal        inheritance      hollow triangle
Dog ------|>  IPet          realization      dashed + hollow triangle
House *----   Room          composition      filled diamond
Team  o----   Player        aggregation      hollow diamond
Student ----  Teacher       association      plain line
Printer <---  Document      dependency       dashed arrow
```

The diamond always sits on the **owning** end.

## Multiplicity

```
Team  o---- 1..* Player       a team has one or more players
Student ---- 0..1 Teacher     a student has at most one tutor
Order  *---- 1..* OrderLine   an order has at least one line
```

| Notation | Means |
|---|---|
| `1` | exactly one |
| `0..1` | none or one |
| `*` | any number |
| `1..*` | at least one |
| `2..5` | between 2 and 5 |

## Diagram → code

```
Team o---- 1..* Player                   House *---- 1..* Room

class Team                               class House
{                                        {
    private readonly List<Player>            private readonly List<Room>
        _players = new();          // 1..*       _rooms = new();
    public void Sign(Player p)               public void AddRoom(string n, double a)
        => _players.Add(p);        // GIVEN         => _rooms.Add(new Room(n, a));  // CREATED
}                                        }
```

The **only** difference in code is whether the part is created inside or passed in. That is the
whole distinction between composition and aggregation.

## Choosing

1. Is the child genuinely a **kind of** the parent? → inheritance
2. Can the part exist on its own? → no: composition · yes: aggregation
3. Do I only need it for one call? → dependency (pass it as a parameter)

> When in doubt, prefer composition or dependency over inheritance. See [2.13](2.13.md).
