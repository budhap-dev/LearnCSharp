## The brief

> "A school library lends books to members. A member may borrow up to **3 books** at a time, for
> **14 days**. Borrowing an unavailable book must be refused. Late returns are fined **10p per
> day**. Staff need a report of everything currently overdue."

This lesson applies everything in Module 2 to turn that paragraph into working code.

## Step 1 — find the nouns

| Word | Verdict |
|---|---|
| library | ✅ a class — it coordinates everything |
| book | ✅ a class |
| member | ✅ a class |
| **loan** | ✅ a class — and the interesting one |
| fine | ❌ not a class — it is a *calculation* on a Loan |
| 3 books, 14 days, 10p | ❌ not classes — they are constants and rules |

> **The insight worth taking away.** Beginners put `DueDate` on `Book`. Then a book gets lent
> twice and there is nowhere to store two histories.
>
> When a fact belongs to a **relationship** rather than to a thing, that relationship wants its
> own class. A due date is not a property of a book, nor of a member — it belongs to the *loan*
> that connects them.

## Step 2 — find the verbs

| Verb | Becomes |
|---|---|
| borrow / lend | `Library.Borrow(member, book)` |
| return | `Library.Return(loan)` |
| calculate fine | `Loan.FineOn(date)` |
| report overdue | `Library.OverdueReport(date)` |

## Step 3 — sketch the relationships

```
+----------+          +---------+          +----------+
|  Member  |1      * |  Loan   | *      1 |   Book   |
+----------+----------+---------+----------+----------+
| Name     |          | Due     |          | Title    |
| MaxLoans |          | Returned|          | Author   |
+----------+          +---------+          +----------+

Library  *---- Book        composition: the library owns its stock
Library  *---- Member      composition: it owns its membership list
Library  *---- Loan        composition: a loan means nothing without it
Loan     ----> Book        association: a loan refers to a book
Loan     ----> Member      association: and to a member
```

Notation from [2.12](2.12.md).

## Step 4 — decide where each rule lives

| Rule | Lives in | Why |
|---|---|---|
| "up to 3 books" | `Library` | only it can see *all* of a member's loans |
| "14 days" | `Loan` | it owns the dates |
| "10p per day late" | `Loan.FineOn` | a calculation on its own data |
| "refuse if unavailable" | `Library.Borrow` | it decides; `Book` merely reports its state |

> **The guiding question:** *which object owns the data this rule needs?* Put the rule there.
>
> A rule sitting far away from its data is the main cause of tangled code.

## Step 5 — build it

```csharp
public class Loan
{
    public const int LoanDays = 14;
    public const decimal FinePerDay = 0.10m;

    public Loan(Member member, StockBook book, DateOnly borrowedOn)
    {
        Member = member;
        Book = book;
        BorrowedOn = borrowedOn;
        DueOn = borrowedOn.AddDays(LoanDays);
    }

    public bool IsOpen => ReturnedOn is null;

    public bool IsOverdueOn(DateOnly date) => IsOpen && date > DueOn;

    public int DaysLateOn(DateOnly date) =>
        IsOverdueOn(date) ? date.DayNumber - DueOn.DayNumber : 0;

    public decimal FineOn(DateOnly date) => DaysLateOn(date) * FinePerDay;
}
```


## A bug worth studying

The lesson code originally reported *"returned Dune **0 days late** — fine £0.70"*. Both numbers
came from the same loan, and they disagreed.

The cause: `Return` closed the loan first, and `DaysLateOn` returns 0 once a loan is closed —
which is correct behaviour — so reading it *after* closing gave 0.

```csharp
// Read BOTH values before closing.
int daysLate = loan.DaysLateOn(today);
decimal fine = loan.FineOn(today);

loan.Close(today);
```

**The lesson:** when an object's state change alters what its methods report, the *order* of
your reads becomes part of the logic. This class of bug is invisible until the numbers
contradict each other.

## Step 6 — critique your own design

| Question | Answer |
|---|---|
| Single responsibility? | `Loan` does dates and fines; `Library` does policy. Reasonable. |
| Would a fine change be easy? | Yes — one constant in `Loan`. |
| Would "reserve a book" fit? | Yes — a `Reservation` class beside `Loan`. |
| What is still weak? | `Library` is growing: stock **and** members **and** policy. |
| Next refactor | Extract a `LendingPolicy` (max loans, loan length, fine rate). |

> A first design is never the final one. The measure of a good model is not that it was right
> first time, but that **changing it later is cheap**.

## Your turn

Model a **cinema**: films, screens, showings, seats, bookings.

Start with the question that made `Loan` necessary: *which facts belong to a Showing rather
than to a Film?* (A running time belongs to the film. A start time belongs to the showing.)

Then try: a car park · a quiz app · a bank · a train timetable.

Always: **nouns → classes, verbs → methods, relationship facts → their own class.**
