## The idea

Everything you wrote in Module 1 was **procedural**: a sequence of instructions operating on
loose variables. That works perfectly well — until the program gets big.

**Object-oriented programming** reorganises a program into *objects*: things that own their own
data **and** the rules that protect it.

## The same problem, twice

A library needs to lend books. Procedurally:

```csharp
string[] titles    = ["The Hobbit", "Dune", "Emma"];
bool[]   isOnLoan  = [false, false, false];
string[] borrowers = ["", "", ""];

isOnLoan[0] = true;
borrowers[0] = "Ada";
```

Three arrays that must stay the same length, in the same order, **forever**. Sort one and the
data silently corrupts. Nothing stops you lending a book that is already out. Every rule about
lending lives in whatever code happens to touch these arrays.

Now object-oriented:

```csharp
public class LibraryBook
{
    private string? _borrower;              // private: nobody outside can forge a loan

    public string Title { get; }
    public bool IsOnLoan => _borrower is not null;

    public string Lend(string borrower)
    {
        if (IsOnLoan) return $"refused - already with {_borrower}";

        _borrower = borrower;
        return $"lent to {borrower}";
    }
}
```

```csharp
hobbit.Lend("Ada");     // "lent to Ada"
hobbit.Lend("Cara");    // "refused - already with Ada"
```

The data and the rule that protects it are **in the same place**. The object cannot be put into
an impossible state, because the only way in is through its own methods.

## Finding the objects

Read the requirement and underline the words:

> "A **library** *lends* **books** to **members**. A member can *borrow* up to 3 books. Each
> **loan** has a due date. Overdue loans generate a **fine**."

| Word type | Becomes | Here |
|---|---|---|
| Nouns | candidate classes | Library, Book, Member, Loan |
| Verbs | methods | Lend, Borrow, Return, CalculateFine |
| Adjectives / values | properties | dueDate, isOverdue, maxBooks |

This is a **starting point, not a rule**. Some nouns turn out to be properties (a due date is
not a class). Some turn out to be missing entirely. You will get it wrong first time — everyone
does, and lesson 2.15 is a whole workshop on refining it.

## The four pillars

| Pillar | Means | Lesson |
|---|---|---|
| **Abstraction** | Expose *what* it does, hide *how* | [2.3](2.3.md) |
| **Encapsulation** | Keep data private, guard it with methods | [2.4](2.4.md) |
| **Inheritance** | A new class built on an existing one | [2.5](2.5.md) |
| **Polymorphism** | One call, many behaviours | [2.6](2.6.md) |

The `LibraryBook` above already shows two: you call `Lend("Ada")` without knowing how the loan
is recorded (abstraction), and `_borrower` is private so nobody can forge one (encapsulation).

## Why bother?

- **Manages complexity** — ten classes of 50 lines beat one file of 500.
- **Localises change** — change how fines work and only `Loan` changes.
- **Reuse** — one `Book` class, ten thousand book objects.
- **Testability** — test a `Book` on its own, with no library and no database.
- **Models reality** — the code reads like the problem it solves.

## When *not* to use OOP

- A 20-line script. A class adds ceremony and no value.
- Pure calculation. A `static` method is simpler than an object.
- Data with no rules attached. Use a `record` — [2.9](2.9.md).

> ⚠️ A class called `Manager`, `Helper`, `Processor` or `Data` usually means you have found a
> **verb pretending to be a noun**. Look again for the real object.

## Other paradigms exist

| Paradigm | Idea | Languages |
|---|---|---|
| Procedural | a sequence of instructions on shared data | C, and your Module 1 code |
| Object-oriented | objects owning data and behaviour | C#, Java |
| Functional | pure functions, no shared mutable state | F#, Haskell |

C# is genuinely **multi-paradigm**. LINQ (Module 3) is functional in style, records are close
to it, and a static helper class is plain procedural. Use whichever fits the problem.
