## The brief

Rooms, exits, items, a player with health — the classic text adventure. It looks like a toy;
it is actually the densest integration exercise in the course: interfaces, events, delegates
and a graph, all load-bearing in one program.

| Draws on | For |
|---|---|
| [2.7](../module-2/2.7.md) interfaces | items with different capabilities |
| [1.5](../module-1/1.5.md), [4.6](../module-4/4.6.md) patterns | using items by capability |
| [4.3](../module-4/4.3.md) events | the world reacting to the player |
| [4.1](../module-4/4.1.md)–[4.2](../module-4/4.2.md) delegates | the command table |
| [5.8](../module-5/5.8.md) graphs | the map, and solving it |

## Items: capability, not hierarchy

A key, a potion and a sword share almost nothing — forcing them under one base class would be
the [2.5](../module-2/2.5.md) is-a mistake. Interfaces compose instead:

```csharp
public interface IItem   { string Name { get; } string Describe(); }
public interface IUsable { string Use(Adventurer player); }

public class Key    : IItem          { ... }        // an item, not usable
public class Potion : IItem, IUsable { ... }        // both
```

Using whatever is usable is one type pattern ([4.6](../module-4/4.6.md)):

```csharp
string effect = item switch
{
    IUsable usable => usable.Use(player),
    _ => "nothing happens",
};
```

## Events: the world reacts without being asked

The player announces; whoever cares listens ([4.3](../module-4/4.3.md)):

```csharp
player.HealthChanged += (_, e) => Line($"[event] health {e.Before} -> {e.After}");
player.Died += (_, _) => Line("[event] you have died!");
```

`Adventurer` knows nothing about the UI, sounds or achievements that might subscribe — and
note the guard inside: `Died` fires only when health *crosses* zero, so subscribers never need
to de-duplicate.

## The map is a graph — so it is solvable

Rooms are nodes, exits are edges, stored exactly as [5.8](../module-5/5.8.md)'s adjacency
list. `Connect` writes the reverse exit too, so every corridor works both ways.

Because it *is* a graph, the algorithms come free:

```csharp
world.ShortestRoute("Hall", "Treasury")   // BFS: Hall -> Library -> Cellar -> Treasury
world.Reachable("Hall").Count             // can the player get everywhere? (level design QA!)
```

A "hint" command is just the first step of that BFS route. This is the point of the module:
the data structure was not chosen to be clever — it was chosen because **the problem is a
graph**, and then twenty lines of Module 5 solve level-design problems for free.

## Commands: a dictionary of behaviour

Instead of a giant `switch` on the input string, a table of delegates
([4.2](../module-4/4.2.md)'s calculator pattern, grown up):

```csharp
Dictionary<string, Func<string, string>> commands = new(StringComparer.OrdinalIgnoreCase)
{
    ["look"]      = _ => world.Current.Description,
    ["go"]        = direction => world.Move(direction).Message,
    ["inventory"] = _ => string.Join(", ", player.Inventory.Select(i => i.Name)),
};
```

Adding a verb = adding one entry. The parse loop never changes, and unknown verbs fall out
naturally with `TryGetValue`.

## Extend it yourself

1. Locked doors that need the right `Key` in the inventory — capability checking again.
2. Monsters with an `ICombatant` interface and a turn-based fight.
3. Load the map from a text file ([4.9](../module-4/4.9.md)) so levels need no recompiling.
4. A `hint` command from the BFS route; a `map` command from `Reachable`.
