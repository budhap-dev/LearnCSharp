## The mindset

Users mistype; **attackers craft**. Input validation for users is UX ([1.3](../module-1/1.3.md));
input handling against crafted data is security. Nearly every classic attack is one pattern:
**data crossing into code**.

## SQL injection — the classic

Naive code glues user input into a query:

```csharp
string sql = $"SELECT * FROM Users WHERE Name = '{input}'";
```

The attacker types `' OR '1'='1` as their "name", and the query becomes:

```sql
SELECT * FROM Users WHERE Name = '' OR '1'='1'
```

— true for every row: logged in as everyone. With `'; DROP TABLE Users; --` they delete the
table instead. This one mistake has breached thousands of real systems.

### The fix is total: parameterised queries

```csharp
string sql = "SELECT * FROM Users WHERE Name = @name";
command.Parameters.AddWithValue("@name", input);
```

The input travels as pure **data** — the database never parses it as SQL. There is no input
weird enough to escape a parameter, and it is *less* code than escaping by hand. Every real
database library supports this; using it is non-negotiable.

## Storing passwords

| Approach | Verdict |
|---|---|
| Plaintext | One leak = every account. Indefensible. |
| "Encrypted" | The key sits next to the data — same leak, one extra step. |
| **Hashed** | One-way: you can *check* a password without being able to *recover* it. |

### But a fast hash is still wrong

SHA-256 is built for **speed** ([5.9](../module-5/5.9.md) — file checksums). A GPU tries
billions of guesses per second, and precomputed "rainbow tables" already contain every common
password's hash. Fast hashes protect *files*, not *passwords*.

### Right: a salt plus a deliberately slow hash

```csharp
byte[] salt = RandomNumberGenerator.GetBytes(16);              // random, per user
byte[] hash = Rfc2898DeriveBytes.Pbkdf2(password, salt,
                  100_000, HashAlgorithmName.SHA256, 32);      // 100,000 rounds
```

- The **salt** (stored beside the hash) makes identical passwords hash differently — rainbow
  tables die instantly.
- The **rounds** make one attempt cost real time. Tune for ~100 ms on your hardware: nothing
  to a user logging in once, ruinous across billions of guesses.
- Verification re-runs PBKDF2 with the stored salt, comparing with
  `CryptographicOperations.FixedTimeEquals` — constant-time, so an attacker cannot learn
  bytes from *how quickly* a comparison fails (a timing attack).

PBKDF2 is built into .NET; bcrypt and Argon2 are the same idea, stronger.

## Random vs RandomNumberGenerator

| | `Random` ([1.10](../module-1/1.10.md)) | `RandomNumberGenerator` |
|---|---|---|
| Purpose | games, dice, shuffles | secrets |
| Predictable? | yes — observe outputs, predict the rest | no — OS entropy |

```csharp
RandomNumberGenerator.GetBytes(32)              // session token
RandomNumberGenerator.GetInt32(100_000, 1_000_000)   // reset code
```

**The rule:** anything an attacker would *want* to guess — tokens, reset codes, keys, salts —
comes from `RandomNumberGenerator`. A reset code from `new Random()` is guessable.

## Secrets do not live in source code

`const string ApiKey = "sk-live-..."` is in git **forever** — history survives deletion, and
leaked keys are scraped within minutes. Instead: environment variables locally, a secrets
manager in production, read via `Environment.GetEnvironmentVariable`. (This course practises
it: the Azure deploy token lives in a GitHub secret, not the workflow file.)

## The rest of the essentials

- **Least privilege** — the app's DB account that cannot `DROP TABLE` turns an injection from
  catastrophe into nuisance.
- **Dependencies are code you run** — keep packages updated; known holes get exploited.
- **Error messages** — stack traces to users leak internals ([4.7](../module-4/4.7.md) wraps
  instead); log privately.
- **Do not invent crypto** — use the platform's reviewed primitives, as this lesson does.

## Common mistakes

| Mistake | Consequence |
|---|---|
| String-built SQL | Injection |
| MD5/SHA-256 for passwords | Cracked at GPU speed |
| No salt | One rainbow table cracks every user |
| `Random` for tokens | Predictable secrets |
| Keys committed to git | Scraped and abused within minutes |

## Exercises

   parameterised version and show the same input is inert.
2. Hash the same password twice with different salts and confirm the hashes differ.
3. Time PBKDF2 at 1k / 10k / 100k rounds; pick the rounds giving ~100 ms on your machine.
4. Explain in two sentences why encrypting passwords is barely better than plaintext.
