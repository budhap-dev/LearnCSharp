## The idea

A **thread** is one worker executing your code; a process can have many, sharing one heap.
More threads means using more CPU cores ([4.10](../module-4/4.10.md)'s `Task.Run` borrowed
them already) — and it means **shared mutable state**, which is where the worst bugs in
software live.

## A race condition, live

The lesson runs four threads, each incrementing one counter 100,000 times:

```csharp
int counter = 0;
// four threads, each:
for (int i = 0; i < 100_000; i++)
    counter++;
```

Expected 400,000. Actually reached — on one real run — **164,123**.

The cause: `counter++` is secretly three steps — *read, add one, write back*. Two threads can
both read 500, both compute 501, both write 501: one update lost. Repeat millions of times and
updates vanish wholesale — a **race condition**.

> Race conditions are the worst kind of bug: rare, unrepeatable, invisible in tests, and a
> different wrong answer every run. You do not debug them; you design them out.

## The three fixes

**1. `lock` — one thread at a time:**

```csharp
object gate = new();

lock (gate)
{
    counter++;        // the three steps can no longer interleave
}
```

`lock (gate)` means: wait until nobody holds the gate, take it, run the block, release it.
Correct result, every run.

**2. `Interlocked` — atomic hardware operations:**

```csharp
Interlocked.Increment(ref counter);
```

One indivisible CPU instruction. For counters and simple updates it is both correct **and**
faster than `lock`.

**3. Concurrent collections** — `Dictionary` corrupts under concurrent writes;
`ConcurrentDictionary` is built for them:

```csharp
tallies.AddOrUpdate(key, 1, (_, count) => count + 1);
```

Plus `ConcurrentQueue`, `ConcurrentBag`, `BlockingCollection`.

## Deadlock: the mutual standoff

Thread A holds lock 1 and wants lock 2; thread B holds 2 and wants 1. Both wait forever — no
exception, no crash, just silence. (The lesson describes rather than runs one, for the obvious
reason.)

**The prevention rule:** every thread acquires multiple locks in the **same agreed order**.
A cycle cannot form if everyone climbs the same ladder.

## Parallel.For: real speedup, measured

```csharp
Parallel.For(2, 2_000_000, n =>
{
    if (IsPrime(n)) Interlocked.Increment(ref count);
});
```

The lesson counts two million primality tests both ways — the parallel version wins by
roughly the number of cores. Note the `Interlocked` *inside* the parallel loop: parallelism
does not excuse the race rules; it makes them mandatory.

And the counter-example: parallelising a *tiny* job is **slower** — the coordination costs
more than the work. Parallelise big, independent chunks, and measure ([6.2](6.2.md)).

## Thread vs Task — what you actually use

| Tool | Use for |
|---|---|
| `new Thread(...)` | almost never, today |
| `Task.Run` | CPU work off the current thread ([4.10](../module-4/4.10.md)) |
| `async`/`await` | I/O waiting, no thread held at all |
| `Parallel.For`/`ForEach` | data parallelism over a collection |

## The safety rules

1. **Prefer no shared state** — give each thread its own data, combine at the end.
2. **Immutable data needs no locks** — records ([2.9](../module-2/2.9.md)) shine here.
3. Must mutate? `lock`, `Interlocked`, or a concurrent collection.
4. Multiple locks? One agreed order, everywhere.
5. Never assume parallel is faster — **time it**.

## Common mistakes

| Mistake | Result |
|---|---|
| `counter++` from several threads | Lost updates |
| Locking on `this` or a string | Outsiders can lock the same object — use a private `object` |
| Plain `Dictionary` under concurrent writes | Corruption, eventually |
| Different lock orders in different methods | Deadlock, one day, in production |
| Parallelising tiny work | Slower than sequential |

## Exercises

1. Reproduce the race with two threads and 10,000 increments; run it five times and record
   the five different answers.
2. Fix it three ways — `lock`, `Interlocked`, and no-shared-state (each thread its own
   subtotal) — and time all three.
3. Use `Parallel.For` to sum square roots of 1..10 million; verify against sequential.
4. Write on paper the lock-order rule that would prevent A/B deadlock in a `Transfer(from,
   to)` bank method that locks both accounts.
