## From principle to container

[2.13](../module-2/2.13.md) taught the **principle**: depend on interfaces, take dependencies
as constructor parameters. At small scale you wire by hand — and should:

```csharp
var service = new ReportService(
    new SqlOrderStore(new ConnectionFactory("server=prod")),
    new PdfRenderer(),
    new SmtpMailer(new ConnectionFactory("server=prod")));
```

Four objects already need careful ordering and a shared factory. Real applications have
*hundreds*, and every new constructor parameter ripples through every place that builds the
object. **The wiring becomes the maintenance burden** — that is the problem a container
solves, and the only one.

## The container

Describe the recipe once:

```csharp
ServiceCollection services = new();
services.AddSingleton<ConnectionFactory>(_ => new ConnectionFactory("server=prod"));
services.AddSingleton<IOrderStore, SqlOrderStore>();
services.AddSingleton<IRenderer, PdfRenderer>();
services.AddSingleton<IMailer, SmtpMailer>();
services.AddTransient<ReportService>();

using ServiceProvider provider = services.BuildServiceProvider();
```

Resolve anywhere:

```csharp
ReportService service = provider.GetRequiredService<ReportService>();
```

The container reads `ReportService`'s constructor (by reflection —
[4.11](../module-4/4.11.md)), sees it needs an `IOrderStore`, an `IRenderer` and an
`IMailer`, builds each (and *their* dependencies), and hands back the finished graph. Add a
fifth parameter tomorrow and **nothing else changes**.

This is `Microsoft.Extensions.DependencyInjection` — the same container ASP.NET is built on,
so `AddSingleton`/`AddScoped` in any web tutorial is exactly this lesson.

## The three lifetimes

The lesson proves each with counters:

| Lifetime | Instances | Measured | Use for |
|---|---|---|---|
| **Singleton** | one, ever | `#1` then `#1`, `#1` in a new scope too | config, caches — must be **thread-safe** ([6.1](6.1.md)) |
| **Scoped** | one per scope | `#1` twice in scope 1; `#2` in scope 2 | per-request state (in ASP.NET, a scope *is* a request) |
| **Transient** | new every resolve | `#1` then `#2` | cheap, stateless services — the safe default |

## The composition root

**All registration happens in one place, at startup.** Everywhere else, classes just declare
constructor parameters; nobody calls `new`, and nobody touches the container.

The anti-pattern is the **service locator** — passing the provider around and calling
`GetService` inside classes. It hides dependencies all over again, which is precisely what
constructor injection was fixing: a dependency belongs in the *signature*, visible.

## Testing: the point, restated

```csharp
var testable = new ReportService(new FakeOrderStore(), new PdfRenderer(), new RecordingMailer());
```

No container in sight. DI the *principle* is what makes testing possible; the *container* is
convenience at scale. Tests usually skip it and pass fakes directly — exactly the
[2.13](../module-2/2.13.md) `RecordingSender` move.

## When a container is overkill

| Situation | Verdict |
|---|---|
| Console tool, five classes | `new` them in Main — done |
| This course's 62 lessons | no container anywhere; none needed |
| An ASP.NET application | the framework hands you this container on day one |

The judgement to carry: **the principle always; the container when the wiring hurts.**

## Common mistakes

| Mistake | Why it bites |
|---|---|
| Injecting `ServiceProvider` itself | Service locator — hidden dependencies again |
| Stateful singleton without thread safety | Every request shares it ([6.1](6.1.md)) |
| Scoped service captured by a singleton | Outlives its scope — subtle corruption |
| Registering everything singleton "for speed" | Shared state you never meant to share |
| Using the container in unit tests | Fakes passed directly are simpler and clearer |
