## The idea

An array is one contiguous block — which is why indexing is O(1) and why inserting means
shuffling. A **linked list** abandons contiguity: separate nodes, each holding a value and a
pointer to the next.

```
head
 |
 v
[10|.]-->[20|.]-->[30|/]        '/' = null: the end
```

```csharp
public class Node<T>
{
    public Node(T value) => Value = value;

    public T Value { get; set; }
    public Node<T>? Next { get; set; }
}
```

That is the whole building block. A list is just a `_head` reference (and, for O(1) appends, a
`_tail`), plus code that walks the arrows.

```diagram
linked-list
```

You used .NET's `LinkedList<T>` in [3.3](../module-3/3.3.md); this lesson builds one so you
can see inside — because **trees and graphs are made of exactly this node-and-pointer idea**.

## The operations, and why each costs what it costs

**Add at the front — O(1):**

```csharp
public void AddFirst(T value)
{
    Node<T> node = new(value) { Next = _head };   // point the new node at the old head
    _head = node;                                  // it IS the head now
    _tail ??= node;
    Count++;
}
```

No shuffling, ever — an array would move every element. Two pointer writes.

**Add at the end — O(1) with a tail pointer**, O(n) without (you would walk the whole chain to
find the end).

**Insert after a known node — O(1):**

```csharp
current.Next = new Node<T>(value) { Next = current.Next };
```

Re-point two arrows and the chain heals around the newcomer. *Finding* the node is the O(n)
part.

**Remove — re-point past it:**

```csharp
if (previous is null) _head = current.Next;    // removing the head is special
else previous.Next = current.Next;             // otherwise: skip over the node
```

Note the pattern: you must track `previous` while walking, because a singly-linked node cannot
see backwards. Edge cases — head, tail, single item — are where linked-list bugs live.

**Search / index — O(n), always.** No index arithmetic exists; you walk.

## Reversing in one pass — the classic

Walk the chain turning every arrow around:

```csharp
public void Reverse()
{
    Node<T>? previous = null;
    Node<T>? current = _head;

    while (current is not null)
    {
        Node<T>? next = current.Next;    // 1. remember where we were going
        current.Next = previous;         // 2. turn the arrow around
        previous = current;              // 3. advance both pointers
        current = next;
    }

    _head = previous;
}
```

Three pointers, one pass, O(1) space. Worth tracing by hand on paper until it clicks — it is
*the* pointer-manipulation exercise, and a perennial interview question for that reason.

## Doubly linked: arrows both ways

```
null<--[10|.]<-->[20|.]<-->[30|.]-->null
```

Each node also points `Previous`. The price: one extra pointer per node and twice the wiring to
keep consistent. The purchase: walking backwards, and **O(1) removal of a known node** —
`_tail.Previous` is reachable, so `RemoveLast` needs no walk. Browser back/forward history is
the canonical use.

## The honest comparison

| Operation | Array / `List<T>` | Linked list |
|---|---|---|
| Access by index | **O(1)** | O(n) |
| Insert/remove at front | O(n) | **O(1)** |
| Insert/remove at end | O(1) amortised | O(1) with tail |
| Insert mid, once located | O(n) shuffle | **O(1)** |
| Search | O(n) | O(n) |
| Memory per item | value only | value + pointer(s) |
| Cache behaviour | **excellent** | poor |

And the practical verdict from [3.3](../module-3/3.3.md) still stands: contiguous arrays are so
friendly to modern CPU caches that `List<T>` usually wins **even where the table says it
shouldn't**. You learn linked lists because the *concept* — objects referencing objects — is
the foundation of every structure in the rest of this module.

## Implementing IEnumerable

Ten lines make the hand-built list a first-class citizen:

```csharp
public IEnumerator<T> GetEnumerator()
{
    for (Node<T>? current = _head; current is not null; current = current.Next)
        yield return current.Value;
}
```

`foreach`, `Where`, `Sum` — all of Module 3 now works on it. This is [3.5](../module-3/3.5.md)
paying off.

## Common mistakes

| Mistake | Result |
|---|---|
| Losing the head reference | The whole list is garbage-collected |
| Forgetting `next` before re-pointing (reverse) | The rest of the chain is lost |
| Not special-casing head/tail removal | Null references or orphaned tails |
| Forgetting to update `Count`/`_tail` | Lies later |
| Using linked lists "for performance" untested | `List<T>` probably wins — measure |

## Exercises

1. Trace `Reverse()` on `[1,2,3]` on paper: draw every arrow after each iteration.
2. Add `RemoveFirst()` and `RemoveLast()` to the singly-linked list. Which is O(n), and why?
3. Write `FindMiddle()` using the two-pointer trick (one walker moves twice as fast).
4. Detect a cycle: make the tail point back into the chain, then implement Floyd's
   tortoise-and-hare.
5. Merge two sorted linked lists into one sorted list — the [5.3](5.3.md) merge, on pointers.
