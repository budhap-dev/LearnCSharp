## The idea

Searching means comparing — unless you can **compute where the item lives from the item
itself**:

```
index = hash(key) % tableSize
```

A **hash function** turns a key into a number; `%` folds it into the array
([1.4](../module-1/1.4.md)'s wrap-around, one last time). Then you jump straight to that slot:
O(1). This is the machinery you have been trusting since [3.2](../module-3/3.2.md) — this
lesson opens the box.

## What makes a hash function good

| Property | Why |
|---|---|
| deterministic | the same key must always land in the same slot |
| fast | or the O(1) is a lie |
| well spread | keys should fill the table evenly |
| uses the whole key | or whole families of keys collide |

The lesson shows a classic failure — summing the letters:

```csharp
static int SimpleHash(string key)      // BAD
{
    int total = 0;
    foreach (char c in key) total += c;
    return total;
}

SimpleHash("abc")   // 294
SimpleHash("cba")   // 294  <- every anagram collides!
```

Order is ignored, so `"abc"` and `"cba"` are identical. The standard fix — multiply by a prime
as you go — makes position matter:

```csharp
static int BetterHash(string key)
{
    int hash = 17;
    foreach (char c in key) hash = hash * 31 + c;
    return Math.Abs(hash);
}
```

This is essentially what `string.GetHashCode` does.

## Collisions are mathematically unavoidable

Infinitely many possible keys, finitely many slots: clashes **must** happen (the pigeonhole
principle — and the birthday paradox says they happen sooner than intuition expects: 23 people,
50% chance of a shared birthday). A hash table is defined by how it copes.

### Strategy 1: separate chaining — what .NET uses

Each slot holds a *list* of entries:

```
slot 0: ("Ada", 91)
slot 1: (empty)
slot 2: ("Ben", 64) -> ("Cara", 78)      <- both hashed to 2; the chain absorbs it
```

Lookup: hash to the slot, then walk the (short) chain comparing keys. This two-step is
exactly why `Equals` and `GetHashCode` are partners ([2.10](../module-2/2.10.md)) — the hash
picks the bucket, `Equals` picks within it.

### Strategy 2: open addressing — linear probing

No chains; on collision, try the next slot along, wrapping at the end:

```
slot 1: ("Dev", 55)    home slot 1
slot 3: ("Ben", 64)    home slot 3
slot 4: ("Cara", 78)   home slot 4
```

Lookup probes from the home slot until it finds the key **or an empty slot** — empty means
"definitely not here", which is why deletion needs care (a naive removal breaks other keys'
probe chains).

## Load factor: when to grow

**load factor = items / slots.** Low: mostly empty, collisions rare. High: chains lengthen,
probing degrades, O(1) rots toward O(n). The lesson fills a 4-slot table and watches the
longest chain grow with the load.

The remedy is resizing — a bigger table and **re-hash every key**, because `hash % newSize`
lands everywhere differently. Like `List<T>`'s doubling ([3.1](../module-3/3.1.md)): occasional
O(n) buys amortised O(1). `Dictionary` resizes itself around 0.7ish; that is why it stays fast
without your help.

| Case | Insert / lookup / delete |
|---|---|
| average | **O(1)** |
| worst (all keys collide) | O(n) |

The price of O(1): **order is lost**. A hash table has none; use `SortedDictionary` — the
red-black tree from [5.7](5.7.md) — when order matters. The full trade: hashing O(1) unordered,
trees O(log n) sorted.

## GetHashCode in practice

```csharp
42.GetHashCode()               // fine, stable
HashCode.Combine(x, y)         // combining fields properly (2.10)
"Ada".GetHashCode()            // DIFFERENT each run!
```

> ⚠️ String hash codes are deliberately **randomised per process** (a defence against
> hash-flooding attacks). Never persist one to a file or database — it will not match
> tomorrow.

### The contract, and the mutable-key disaster

The lesson buries a key alive:

```csharp
Dictionary<MutableKey, string> map = new();
MutableKey key = new("original");
map[key] = "the value";

key.Name = "changed";          // the hash code just changed...
map.ContainsKey(key)           // false! entry filed under the OLD hash
```

The entry still *exists* — in a bucket nobody will ever look in again. This is the concrete
disaster behind three rules you have already met: `Equals`⇔`GetHashCode` consistency
([2.10](../module-2/2.10.md)), immutable keys, and records/strings being ideal keys
([2.9](../module-2/2.9.md)).

## Hashing beyond hash tables

| Use | Hash type |
|---|---|
| password storage | **slow, salted** (bcrypt/Argon2) — never MD5/SHA alone, never plaintext |
| file integrity / downloads | SHA-256 checksums |
| git commits | content hashes — the id *is* the hash |
| caching / deduplication | fast hashes as fingerprints |

> Cryptographic hashes and hash-table hashes solve **opposite** problems: one must be slow and
> irreversible, the other as fast as possible. Never substitute one for the other —
> [6.3](../module-6/6.3.md) takes up the security story.

## Common mistakes

| Mistake | Result |
|---|---|
| Hash ignoring order/parts of the key | Families of collisions |
| Mutating a key while it is in a dictionary | Entry lost forever |
| Persisting string hash codes | Different next run |
| Expecting iteration order | There is none |
| MD5 for passwords | Crackable at billions/second |
