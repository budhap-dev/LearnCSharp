## Why five algorithms for one job

Because they make different trades — of time, memory, stability and simplicity — and because
AQA examines bubble, insertion and merge specifically. The lesson traces each on
`[5, 2, 9, 1, 7, 3]`, then races them on thousands of items so the theory has numbers attached.

## Bubble sort — swap neighbours until calm

Repeatedly walk the array, swapping any adjacent pair in the wrong order. Each pass bubbles
the largest remaining value to the end.

```csharp
for (int pass = 0; pass < data.Length - 1; pass++)
{
    bool swapped = false;

    for (int i = 0; i < data.Length - 1 - pass; i++)    // the sorted tail shrinks
    {
        if (data[i] > data[i + 1])
        {
            (data[i], data[i + 1]) = (data[i + 1], data[i]);
            swapped = true;
        }
    }

    if (!swapped) break;                                // a calm pass = sorted - stop
}
```

```
start:  5, 2, 9, 1, 7, 3
pass 1: 2, 5, 1, 7, 3, 9
pass 2: 2, 1, 5, 3, 7, 9
pass 3: 1, 2, 3, 5, 7, 9
pass 4: 1, 2, 3, 5, 7, 9   (no swaps - stop)
```

O(n²) worst and average; O(n) best (already sorted, thanks to the `swapped` flag). In-place,
stable, and mainly of educational value.

## Insertion sort — grow a sorted region on the left

Take each item and slide it left into its place among the already-sorted items — how most
people sort playing cards.

```csharp
for (int i = 1; i < data.Length; i++)
{
    int current = data[i];
    int j = i - 1;

    while (j >= 0 && data[j] > current)     // shuffle bigger items right
    {
        data[j + 1] = data[j];
        j--;
    }

    data[j + 1] = current;
}
```

O(n²) worst — but **O(n) on nearly-sorted data**, and genuinely the fastest choice for small
arrays. The lesson proves both claims: on 8,000 nearly-sorted items insertion finishes in ~0 ms
while selection sort grinds through its full quadratic work regardless.

## Selection sort — repeatedly pick the smallest

Scan for the minimum of the unsorted region, swap it into place, repeat.

O(n²) in **every** case — it cannot exploit luck. Its one virtue: fewest swaps of any of these
(n − 1), which mattered when writes were expensive. Know it, then move on.

## Merge sort — divide and conquer

Split in half, sort each half (recursively — [5.4](5.4.md)), then **merge** two sorted halves
by repeatedly taking the smaller front item.

```
split:   [5,2,9,1,7,3]
         [5,2,9]        [1,7,3]
         [5] [2,9]      [1] [7,3]
merge:   [2,5,9]        [1,3,7]
         [1,2,3,5,7,9]
```

```csharp
static int[] MergeSort(int[] data)
{
    if (data.Length <= 1) return data;               // base case

    int middle = data.Length / 2;
    return Merge(MergeSort(data[..middle]), MergeSort(data[middle..]));
}
```

O(n log n) in **all** cases — log n levels of splitting, n work of merging per level. Stable.
The cost: O(n) extra memory for the merging.

## Quicksort — partition around a pivot

Pick a pivot, sweep everything smaller to its left and larger to its right (the pivot is now
*finally placed*), then recurse on each side.

O(n log n) average and usually the fastest in practice — it works in place with beautiful
cache behaviour. The catch: a consistently bad pivot (e.g. last-element pivot on already-sorted
data) degrades it to O(n²).

## The race — theory made visible

From the lesson, random data:

```
                    n = 2,000     n = 8,000
bubble sort            5.8 ms       75.7 ms      x13 for x4 data
insertion sort         1.6 ms       23.3 ms      x15
selection sort         2.7 ms       37.6 ms      x14
merge sort             0.3 ms        1.1 ms      x4
Array.Sort             0.1 ms        0.3 ms      x3
```

Quadruple the data: the O(n²) sorts slow ~16×, the O(n log n) sorts ~4×. The gap only widens —
at a million items the bubble sort would take half an hour; merge sort, a quarter of a second.

## The summary table

| Sort | Best | Average | Worst | Space | Stable |
|---|---|---|---|---|---|
| Bubble | O(n) | O(n²) | O(n²) | O(1) | ✅ |
| Insertion | O(n) | O(n²) | O(n²) | O(1) | ✅ |
| Selection | O(n²) | O(n²) | O(n²) | O(1) | ❌ |
| Merge | O(n log n) | O(n log n) | O(n log n) | O(n) | ✅ |
| Quick | O(n log n) | O(n log n) | O(n²) | O(log n) | ❌ |

**Stable** = equal items keep their original order — it matters when sorting by one key after
another (sort by name, then by year: stability preserves the name order within each year).

## What .NET actually uses

`Array.Sort`/`List.Sort` use **introsort**: quicksort that switches to heapsort if recursion
goes too deep (killing the O(n²) case) and to insertion sort for small partitions — the best of
three worlds. LINQ's `OrderBy` is a **stable** sort that returns a new sequence.

**In real code: use the built-ins.** You learn these five to understand costs, to pass exams,
and to recognise the ideas — divide-and-conquer and partitioning appear everywhere, not just in
sorting.

## Common mistakes

| Mistake | Result |
|---|---|
| Forgetting the `swapped` early-exit | Bubble loses its O(n) best case |
| Merging by concatenating then re-sorting | O(n² log n) — the merge IS the algorithm |
| Quicksort pivot = last element on sorted data | The O(n²) worst case, reliably |
| Assuming `Sort` is stable | `Array.Sort` is not; `OrderBy` is |

## Exercises

1. Trace insertion sort on `[7, 3, 5, 1]` by hand — every comparison and shift.
2. Implement bubble sort counting comparisons and swaps; run on sorted, reversed and random
   input and tabulate.
3. Implement merge sort for `string[]` using `CompareTo`.
4. Show stability mattering: sort `(name, year)` records by name then by year with a stable
   and an unstable sort; compare the outputs.
5. Feed sorted data to your quicksort with a last-element pivot and watch the time explode;
   then fix it with a middle or random pivot.
