## The idea

Two programs both "work". One answers in a millisecond, the other in an hour. **Big-O
notation** is the language for that difference: it describes **how the work grows as the input
grows**, ignoring the machine, the language and the constant factors.

## The classes you must know

| Class | Name | Growth | Example |
|---|---|---|---|
| O(1) | constant | size makes no difference | `dict[key]`, `array[i]` |
| O(log n) | logarithmic | halving each step | binary search |
| O(n) | linear | one pass | linear search, `Sum()` |
| O(n log n) | linearithmic | the best a general sort can do | merge sort, `Array.Sort` |
| O(n²) | quadratic | nested loops | bubble sort, comparing every pair |
| O(2ⁿ) | exponential | doubles per extra item | naive recursive Fibonacci |
| O(n!) | factorial | every ordering | brute-force travelling salesman |

What that means at n = 100,000:

```
O(log n)          ~17 steps
O(n)          100,000 steps
O(n log n)  ~1,700,000 steps
O(n²)   10,000,000,000 steps      <- hours versus milliseconds
```

## Measured, not just asserted

The lesson races linear search against binary search as the data quadruples:

```
n =   100,000, 200 searches   linear  ~14 ms    binary  0 ms
n =   400,000, 200 searches   linear  ~56 ms    binary  0 ms
n = 1,600,000, 200 searches   linear ~220 ms    binary  0 ms
```

Four times the data → four times slower for O(n). Binary search barely moves: 1.6 million
items need only ~21 comparisons. **This is the shape of the curve made physical.**

## Working out Big-O

Five rules cover nearly everything:

1. **Drop constants.** O(2n) is O(n) — doubling does not change the shape.
2. **Drop lower terms.** O(n² + n) is O(n²) — n² dominates as n grows.
3. **Sequential loops add:** loop n, then loop n → still O(n).
4. **Nested loops multiply:** loop n inside loop n → O(n²).
5. **Halving means log:** `while (n > 1) n /= 2` → O(log n).

Apply them:

```csharp
for (i..n) sum += a[i];                    // O(n)
for (i..n) for (j..n) ...                  // O(n²)
for (i..n) for (j..i) ...                  // O(n²)  - n(n+1)/2, constants drop
while (n > 1) n /= 2;                      // O(log n)
for (i..n) binarySearch(...)               // O(n log n)
list.Contains(v)                           // O(n)
dict.ContainsKey(k)                        // O(1)   - the 3.2 lesson, explained
```

## Best, average, worst

Linear search for the *first* item: 1 step. For the *last*: n steps. Missing entirely: n steps.

Big-O conventionally describes the **worst case**, because that is the guarantee you can plan
around. When average and worst differ dramatically (quicksort: O(n log n) average, O(n²)
worst), say both.

## Space complexity

The same notation for memory:

| Algorithm | Extra space |
|---|---|
| bubble sort | O(1) — sorts in place |
| merge sort | O(n) — temporary arrays |
| recursion | O(depth) of stack — deep recursion overflows ([5.4](5.4.md)) |

Time and space often trade against each other: memoisation in [5.4](5.4.md) buys O(n) time for
O(n) memory.

## Why you personally care

- Choosing `Dictionary` over `List.Contains` in a loop turned minutes into milliseconds in
  [3.2](../module-3/3.2.md) — that *was* Big-O.
- An O(n²) loop is invisible at 100 items and fatal at 100,000. Test data hides it; Big-O
  predicts it.
- AQA asks you to compare algorithm efficiency in exactly this language.

## Common mistakes

| Mistake | Correction |
|---|---|
| "O(1) means fast" | It means *constant* — one slow constant step is still O(1) |
| Counting both loops of `for..n; for..n` as O(n²) | Sequential loops add: O(n) |
| Judging from timings on tiny inputs | Constants dominate small n — grow the input |
| Forgetting hidden loops | `list.Contains` inside a loop is the classic accidental O(n²) |
