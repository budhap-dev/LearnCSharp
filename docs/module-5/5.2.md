## Linear search — check every item in turn

```csharp
static int LinearSearch(int[] data, int target)
{
    for (int i = 0; i < data.Length; i++)
        if (data[i] == target) return i;

    return -1;                              // the agreed "not found"
}
```

O(n), and its virtue is what it does **not** need: the data can be unsorted, and it works on
anything you can enumerate. `Array.IndexOf`, `List.IndexOf` and LINQ's `First` are all linear
searches in a suit.

## Binary search — halve the problem every step

If the data is **sorted**, you can do enormously better. Compare with the middle item: too
small → discard the entire left half; too big → discard the right. Repeat.

```csharp
static int BinarySearch(int[] data, int target)
{
    int low = 0;
    int high = data.Length - 1;

    while (low <= high)
    {
        int middle = low + (high - low) / 2;

        if (data[middle] == target) return middle;
        if (data[middle] < target) low = middle + 1;     // discard the left half
        else high = middle - 1;                          // discard the right half
    }

    return -1;
}
```

Watch it run (from the lesson, searching for 71 in 7 items):

```
looking for 71 in [8, 17, 23, 42, 55, 71, 93]
step 1: range [0..6], middle index 3 = 42 -> too small, search the right half
step 2: range [4..6], middle index 5 = 71 -> FOUND
```

Each comparison halves what remains, so the worst case is **⌈log₂ n⌉** comparisons:

| Items | Worst case |
|---|---|
| 1,000 | 10 |
| 1,000,000 | 20 |
| 1,000,000,000 | **30** |

A billion sorted items, thirty questions. That is the power of halving — and why "guess my
number between 1 and 100" is beatable in seven guesses (project [7.1](../module-7/7.1.md)).

## Why the midpoint is written that way

```csharp
int middle = (low + high) / 2;           // can OVERFLOW when both are huge
int middle = low + (high - low) / 2;     // same value, cannot overflow
```

`low + high` can exceed `int.MaxValue` on giant arrays — a real bug that sat in the JDK's
binary search for years. The second form is free insurance; write it by habit.

## Loop and off-by-one traps

Binary search is famously easy to get *almost* right. The three invariants:

- loop while `low <= high` (not `<` — a one-item range is still searchable)
- move to `middle + 1` / `middle - 1` (not `middle` — or you loop forever)
- recheck your bounds when adapting it (first-match, insertion point, etc.)

The recursive version in the lesson makes the structure explicit: base case "empty range",
recursive case "one half".

## The cost of sorting changes the decision

Binary search needs sorted data, and sorting costs O(n log n) ([5.3](5.3.md)):

| Situation | Best choice |
|---|---|
| One search of unsorted data | linear — sorting first costs more than it saves |
| Many searches of the same data | sort once, then binary every time |
| Data already sorted | binary, always |
| Many lookups **by key** | build a `Dictionary` once — O(1) beats even O(log n) ([3.2](../module-3/3.2.md)) |

## The built-ins

```csharp
Array.BinarySearch(sorted, 55)     // index if found
Array.BinarySearch(sorted, 20)     // NEGATIVE if missing - and useful:
```

A negative result is the **bitwise complement of the insertion point**: `~(-3) == 2` means "20
belongs at index 2". That makes insert-in-sorted-order a two-liner.

```csharp
Array.IndexOf(data, 93)            // linear, unsorted fine
pupils.First(p => p.Name == "Ben") // LINQ - linear with a predicate
```

## Common mistakes

| Mistake | Result |
|---|---|
| Binary search on unsorted data | Wrong answers, no error — the worst kind |
| `(low + high) / 2` | Overflow on huge arrays |
| `while (low < high)` | Misses one-item ranges |
| `high = middle` instead of `middle - 1` | Infinite loop |
| Forgetting the negative-means-insertion-point convention | Treating -3 as a plain failure |
