## The idea

A recursive method calls itself — on a **smaller** version of the problem — until it reaches a
case small enough to answer directly.

Every recursive method needs exactly two things:

1. a **base case** — a size it can answer without recursing
2. a **recursive case** — which must move *towards* the base case

```csharp
static long Factorial(int n)
{
    if (n <= 1) return 1;              // base case
    return n * Factorial(n - 1);       // recursive case: n shrinks
}
```

```
Factorial(4)
= 4 * Factorial(3)
= 4 * (3 * Factorial(2))
= 4 * (3 * (2 * Factorial(1)))
= 4 * (3 * (2 * 1))          <- base case reached; now it unwinds
= 24
```

The lesson prints this trace with real indentation — watch the calls stack up and unwind.

## The call stack is doing the bookkeeping

Each call gets its own **stack frame** — its own `n`, its own place to resume. That is the same
call stack from [1.11](../module-1/1.11.md); recursion is just the stack earning its keep.

Which is also the limit: frames are finite (~1 MB). No base case — or too deep a descent — and
you get `StackOverflowException`, the one exception you **cannot catch**. The lesson measures a
safe depth in the tens of thousands.

## Recursion vs iteration

Anything recursive can be rewritten with a loop, and vice versa:

```csharp
static long FactorialLoop(int n)
{
    long result = 1;
    for (int i = 2; i <= n; i++) result *= i;
    return result;
}
```

Recursion is not faster — it is chosen when it makes the code **clearer**. For a flat
accumulation like factorial, the loop is arguably clearer. The cases where recursion genuinely
shines come below.

## Where naive recursion goes catastrophically wrong

```csharp
static long Fib(int n) => n <= 1 ? n : Fib(n - 1) + Fib(n - 2);
```

Correct — and exponential. Each call spawns two more; the same values are recomputed
endlessly. The lesson counts the calls:

```
Fib(20)     21,891 calls
Fib(25)    242,785 calls        <- x11 for +5
Fib(50)    would take years
```

### Memoisation: remember what you already know

```csharp
static long Fib(int n, Dictionary<int, long> cache)
{
    if (n <= 1) return n;
    if (cache.TryGetValue(n, out long known)) return known;

    long result = Fib(n - 1, cache) + Fib(n - 2, cache);
    cache[n] = result;
    return result;
}
```

`Fib(50)` now computes each value **once**: 49 entries, instant answer. O(2ⁿ) → O(n) for the
price of a dictionary — the time/space trade from [5.1](5.1.md), and the [3.2](../module-3/3.2.md)
dictionary earning its place again.

## The classic small recursions

Each is one honest base case plus one shrinking step:

```csharp
static int Gcd(int a, int b) => b == 0 ? a : Gcd(b, a % b);           // Euclid
static string Reverse(string s) => s.Length <= 1 ? s : Reverse(s[1..]) + s[0];
static int CountDigits(int n) => n < 10 ? 1 : 1 + CountDigits(n / 10);
static long Power(int b, int e) => e == 0 ? 1 : b * Power(b, e - 1);
```

## Where recursion genuinely shines: recursive data

A folder contains folders, which contain folders. The **data** is recursive, so recursive code
fits it like a glove:

```csharp
static int TotalSize(Folder folder) =>
    folder.Files.Sum(f => f.SizeKb) + folder.Folders.Sum(TotalSize);
```

One line traverses a tree of any depth. The iterative version needs an explicit
`Stack<Folder>` and twice the code. The same shape powers trees ([5.7](5.7.md)), graphs
([5.8](5.8.md)), JSON parsing, and merge sort's divide-and-conquer ([5.3](5.3.md)).

Towers of Hanoi is the theatrical version: move n−1 out of the way, move the big disc, move
n−1 back — 2ⁿ−1 moves, and 64 discs would outlast the universe.

## Choosing

| Situation | Choose |
|---|---|
| Trees, folders, nested structures | recursion — it matches the data |
| Divide-and-conquer algorithms | recursion |
| Simple counting / accumulating | a loop |
| Depth could be huge (millions) | a loop with an explicit `Stack<T>` |
| Overlapping subproblems | recursion **with memoisation** |

## Common mistakes

| Mistake | Result |
|---|---|
| No base case | `StackOverflowException` — uncatchable |
| A step that does not shrink the problem | Same |
| Naive recursion on overlapping subproblems | Exponential time (the Fib trap) |
| Deep recursion on user-sized input | Overflow on the unlucky day |
