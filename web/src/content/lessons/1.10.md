## Implicit conversion — always safe, automatic

If the destination can hold **every** possible source value, C# converts silently. Nothing can
be lost, so no permission is needed.

```
byte -> short -> int -> long -> float -> double
char -> int
```

```csharp
byte small = 42;
int medium = small;      // fine
long large = medium;     // fine
double wide = large;     // fine
```

## Explicit cast — you accept the risk

```csharp
double price = 9.99;
int pounds = (int)price;    // 9
```

> ⚠️ A cast **truncates towards zero**. It does **not** round.
> `(int)9.99` is `9`, and `(int)-9.99` is `-9`.

A value that does not fit wraps around silently:

```csharp
(byte)300      // 44  - only the bottom 8 bits survive
```

## Rounding properly

```csharp
Math.Round(9.5)        // 10
Math.Round(8.5)        // 8   <- surprised?
```

.NET uses **banker's rounding** by default: exact halves go to the nearest **even** number. It
stops a long list of `.5` values drifting upwards. Ask for the school rule explicitly:

```csharp
Math.Round(8.5, MidpointRounding.AwayFromZero)   // 9
Math.Round(3.14159, 2)                           // 3.14
Math.Floor(9.99)      // 9    always down
Math.Ceiling(9.01)    // 10   always up
Math.Floor(-9.99)     // -10  down means DOWN
Math.Truncate(-9.99)  // -9   towards zero
```

## Cast vs Parse vs Convert

| | Works on | Bad input | Doubles |
|---|---|---|---|
| `(int)x` | numbers only | wraps | **truncates** |
| `int.Parse(s)` | text | **throws** | n/a |
| `int.TryParse(s, out n)` | text | returns `false` | n/a |
| `Convert.ToInt32(x)` | almost anything | throws; `null` → 0 | **rounds** |

```csharp
(int)9.99                 // 9   truncates
Convert.ToInt32(9.99)     // 10  rounds
```

## Number bases — the GCSE binary and hex topic

```csharp
Convert.ToString(202, 2)      // "11001010"
Convert.ToString(202, 16)     // "ca"
Convert.ToInt32("11001010", 2)  // 202
Convert.ToInt32("CA", 16)       // 202

0xCA            // hex literal        = 202
0b1100_1010     // binary literal     = 202
1_000_000       // digit separators - the compiler ignores the underscores
```

## The Math class

| Method | Does |
|---|---|
| `Math.Abs(-7)` | 7 |
| `Math.Max(a, b)` / `Math.Min` | larger / smaller |
| `Math.Pow(2, 10)` | 1024.0 — returns a **double** |
| `Math.Sqrt(144)` | 12 |
| `Math.Cbrt(27)` | 3 |
| `Math.Log2(1024)` | 10 |
| `Math.Log10(1000)` | 3 |
| `Math.Sign(-42)` | −1 |
| `Math.Clamp(150, 0, 100)` | 100 |
| `Math.PI`, `Math.E` | constants |

Trigonometry works in **radians**: convert with `degrees * Math.PI / 180`.

> `Math.Pow` returns a `double`, so `Math.Pow(2, 3)` is `8.0` not `8`. For powers of two,
> `1 << n` is faster and exact.

## Random numbers

```csharp
Random random = new Random();        // seeded from the clock - different every run
Random fixedSeed = new Random(42);   // same seed -> SAME sequence, ideal for testing

int dice = random.Next(1, 7);        // 1 to 6
double fraction = random.NextDouble();  // 0.0 to just under 1.0

Random.Shared.Next(100);             // a ready-made shared instance
```

> ⚠️ **The upper bound is exclusive.** `Next(1, 7)` gives 1–6. Writing `Next(1, 6)` for a dice
> means you never roll a six — a classic bug.

Two more traps:

- Creating `new Random()` inside a loop can produce **identical** numbers, because instances
  created in the same instant may share a seed. Create **one** Random and reuse it, or use
  `Random.Shared`.
- `Random` is **not** cryptographically secure. For passwords or tokens use
  `System.Security.Cryptography.RandomNumberGenerator`.

## Common mistakes

| Mistake | Fix |
|---|---|
| `(int)9.99` expecting 10 | Use `Math.Round` |
| `Math.Round(0.5)` expecting 1 | Banker's rounding — pass `MidpointRounding.AwayFromZero` |
| `Next(1, 6)` for a dice | Upper bound is exclusive: `Next(1, 7)` |
| `new Random()` inside a loop | Create it once, outside |
| `int x = Math.Pow(2, 3);` | `Pow` returns a `double` — cast, or use `1 << 3` |
